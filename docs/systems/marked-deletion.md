# Удаление помеченных объектов

> **TL;DR:** Обработка строит план удаления по графу ссылок. Объект удаляется, если на него ссылаются только объекты, удаляемые вместе с ним. Удаление идёт одной транзакцией, ссылающиеся объекты удаляются первыми, независимые группы изолированы точками сохранения.
> **Тип:** Concept
> **Аудитория:** Developer, AI-Agent
> **Связанные:** [CRUD](crud-pipeline.md), [Связанные документы](related-documents.md), [Транзакции](transactions.md)

## 1. Правило удаления

Пометка удаления обратима, физическое удаление нет. Помеченный объект удаляется, только если всё, что на него ссылается, удаляется в том же запуске. Это правило 1С «Удаление помеченных объектов». Цепочка «договор → контрагент» удаляется за один проход, если помечены и выбраны оба объекта.

`domain.PlanMarkedDeletion` — чистая функция без SQL:

1. Удаляемым считается весь выбор.
2. Объекты с внешней ссылкой исключаются, пока набор не перестанет меняться (наибольшая неподвижная точка).
3. Объекты разных таблиц, которые ссылаются друг на друга по кругу, исключаются: при `NOT DEFERRABLE`-ключах их нельзя удалить ни в каком порядке. Круг внутри одной таблицы допустим: такие объекты удаляются одним `DELETE`, а PostgreSQL проверяет `NO ACTION`-ключ в конце оператора.
4. Оставшиеся объекты делятся на независимые группы, а каждая группа — на слои (алгоритм Кана по компонентам сильной связности). Слой не содержит объектов, на которые ссылается более поздний слой.

| Статус | Значение |
|--------|----------|
| `ready` | На объект никто не ссылается |
| `withGroup` | Ссылаются только объекты, удаляемые в этом же запуске |
| `blocked` | Есть ссылка, которая остаётся. Причина хранится в `reason` |
| `excluded` | Объект помечен, но не выбран |

| Причина `blocked` | Значение |
|-------------------|----------|
| `liveReference` | Ссылается объект без пометки, регистр или системная таблица |
| `notSelected` | Ссылается помеченный объект, который не выбран |
| `chain` | Ссылается выбранный объект, который сам заблокирован |
| `cycle` | Круговая ссылка между таблицами |

Если причин несколько, выбирается самая базовая: `liveReference`, затем `notSelected`, затем `chain`.

## 2. Откуда берутся ссылки

`MarkedObjectsRepo.referenceSources` объединяет два источника:

- **Метаданные.** Поля-ссылки шапки и табличных частей, у которых `ReferenceType` совпадает с целью, а также `parentId` иерархии в собственной таблице. Столбец берётся из `FieldDef.DBColumn`. Метаданные находят ссылки и без внешнего ключа.
- **Внешние ключи схемы.** Ключи `NO ACTION` и `RESTRICT` на таблицу цели, которые метаданные не описали. Ключи `CASCADE` и `SET NULL` удалению не мешают. Строки таблиц вне реестра всегда считаются живыми ссылками (`sourceEntityType: "system"`).

Помеченные источники читаются полностью, они нужны плану. Живые источники ограничены выборкой из 5 на столбец плюс точное число (`liveRefCount`). Источник из табличной части — её документ-владелец.

Удаляются только справочники и документы, у таблицы которых есть `deletion_mark`. Сканирование ограничено 500 объектами на тип (`truncated: true`).

## 3. Выполнение

`DeleteMarked` работает в одной транзакции:

1. Блокирует выбранные строки `FOR UPDATE`: только помеченные и непроведённые. Сущности блокируются по имени, строки по `id`, поэтому параллельные запуски не создают взаимоблокировку. Конкурирующая вставка ссылки с внешним ключом ждёт блокировки.
2. Перестраивает план по заблокированным строкам.
3. Каждую группу выполняет в своей точке сохранения. Внутри слоя сначала удаляются табличные части, потом шапка. Ошибка откатывает всю группу и не трогает остальные.
4. Пишет `catalog.delete` / `document.delete` с `details.operation = "delete_marked"` в журнал событий той же транзакции. Ошибка записи откатывает группу.

Сообщения об ошибках не раскрывают SQL (CWE-209). Подробности пишутся в серверный лог.

## 4. Чтение помеченных объектов

Триггер CDC заполняет `_deleted_at` при установке пометки, а авторизованное чтение по умолчанию скрывает такие строки. Обработка и «Найти ссылки» читают через `ReadIDsWithDeletionMarked` / `ResolveRefsWithDeletionMarked`. Флаг `readaccess.Query.IncludeDeletionMarked` снимает только фильтр мягкого удаления, RBAC, RLS, FLS и CEL продолжают действовать.

## 5. API

| Метод | Путь | Назначение |
|-------|------|------------|
| `GET` | `/api/v1/system/marked-objects` | План, в котором выбраны все помеченные объекты |
| `POST` | `/api/v1/system/marked-objects/plan` | План для `items` (пустой список — ничего не выбрано) |
| `POST` | `/api/v1/system/marked-objects/delete` | Удаление `items` (1–1000), step-up `system.marked_objects.delete` |
| `POST` | `/api/v1/system/find-references` | Ссылки на объект, включая помеченные (`deletionMark`, `posted`) |

Все маршруты требуют роль `admin`.

## 6. Интерфейс

Страница `/admin/marked-objects` по умолчанию выбирает все помеченные объекты. После каждого изменения выбора она перестраивает план на сервере. Строка раскрывается в список «Где используется». Для ссылающегося объекта доступны действия:

- **Пометить на удаление** — для непомеченного справочника или документа. Пометка ставится явно, через обычный `deletion-mark` эндпоинт сущности. В уведомлении есть «Отменить».
- **Выбрать для удаления** — для помеченного, но невыбранного объекта.
- Проведённый документ пометить нельзя, пока не отменено проведение. Записи регистров и системных таблиц пометить нельзя.

Удаление требует подтверждения. Отчёт показывает пропущенные и неудавшиеся объекты с причиной.
