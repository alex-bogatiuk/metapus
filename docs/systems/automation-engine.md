# Подсистема Автоматизации (Automation Engine)

> **TL;DR:** Механизм реакции на бизнес-события или расписание (CRON). Двухфазное выполнение (Evaluate → Deliver), трёхуровневая адресация (Account → Channel → Subscriber) и AES-256 шифрование ключей.

> **Тип:** Concept
> **Аудитория:** Developer, Admin
> **Связанные:** [core-layer.md](core-layer.md)

---

## 1. Трёхуровневая модель доставки

Для безопасного управления доступом используется абстракция из трёх слоёв:

1. **Account (Аккаунт):** Учётные данные (например, Bot Token для Telegram или SMTP логин). Хранит зашифрованный секрет.
2. **Channel (Канал):** Конкретный адрес доставки (например, ID чата в Telegram), привязанный к Аккаунту.
3. **Subscriber (Подписчик):** Связка между Правилом автоматизации и Каналом.

## 2. Двухфазный движок

Бизнес-логика (например, проведение документа) генерирует событие в таблицу `sys_outbox`. Фоновый воркер (Outbox Consumer) подхватывает событие и запускает Automation Engine.

Процесс разбит на две фазы для отказоустойчивости:

### Фаза 1: Evaluate (CPU-bound)
Сбор правил и вычисление.
- Загрузка активных правил для события.
- Проверка Cooldown (защита от спама).
- **Выполнение CEL-условий** (например: `int(doc.totalAmount) > 100000`).
- Рендеринг текста сообщения через Go Templates.
Возвращает список готовых к отправке заданий.

### Фаза 2: Deliver (I/O-bound)
Доставка и запись истории.
- Вызов адаптеров (`TelegramAdapter`, `EmailAdapter`, `WebhookAdapter`).
- Ошибка адаптера сохраняется в `sys_automation_history` и возвращается outbox/durable cron executor для повтора. Успешный финансовый документ не откатывается из-за доставки. Частично успешная рассылка может повториться; см. [worker reliability](../operations/worker-reliability.md).

## 3. Безопасность: Шифрование Учёток

Все токены и пароли в таблице Accounts шифруются по стандарту **AES-256-GCM**.
- Ключ берётся из переменной окружения `AUTOMATION_ENCRYPTION_KEY` (строго 32 байта).
- В БД ложится: `nonce (12 байт) + ciphertext + auth_tag (16 байт)`.
- Учётные данные **никогда не возвращаются** по API (даже админам). Если нужно изменить пароль — отправляется новый Plaintext через API обновления аккаунта (`PUT`).

## 4. Поддерживаемые действия

API, метаданные формы и PostgreSQL разрешают `notify`, `webhook_call` и `generate_report`. Неисполняемые заготовки `chain`, `create_record`, `chainRuleIds` и chain publisher удалены. Если worker встретит неподдерживаемое действие в старой записи, обработка события вернёт ошибку в outbox; ложного подтверждения выполнения нет.

## 5. Точные суммы в условиях и шаблонах

Денежные поля документа содержат строковые минимальные единицы валюты. В CEL используйте `int(doc.totalAmount)` и порог в тех же единицах. `humanAmounts` содержит точные десятичные строки для отображения. Для MinorUnits они появляются только при известном масштабе валюты; CryptoAmount сохраняет строку в исходных единицах токена.

Шаблон ERP-суммы: `{{ money .doc.totalAmount .currency.decimalPlaces }}`. Форматирование использует `types.FormatMinorUnits`, сохраняет весь диапазон int64 и масштабы 0–18. Дробные минимальные единицы, переполнение, небезопасные float64 и отсутствующий/некорректный масштаб приводят к ошибке шаблона. `number` также сохраняет точность целых чисел. Старый helper `currency` удалён.

Create/edit страницы используют общий `AutomationRuleForm`; загрузка записи, версия, запись и dirty-вкладки остаются в `useCatalogForm`. Ошибки загрузки каналов/отчётов отображаются с повтором запроса.
