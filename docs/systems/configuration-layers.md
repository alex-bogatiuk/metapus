# Слои приложения: платформа, базовая конфигурация, надстройка

> **TL;DR:** Приложение Metapus — три слоя. Платформа — механизмы (формы, проведение, регистры, права), как 1С:Предприятие с БСП. Базовая конфигурация — самодостаточная бизнес-логика, как типовая УНФ. Надстройка — необязательная отраслевая специфика над одной конкретной базой. У тенанта ровно одна база и не больше одной надстройки.
> **Тип:** Concept
> **Аудитория:** Developer

## Слои

| Слой | Что это | В репозитории |
|---|---|---|
| Платформа | Механизмы без бизнес-логики: построение форм и списков, проведение, регистры, права, отчёты, печать, загрузка данных | `internal/`, публичный API — `pkg/sdk` |
| Базовая конфигурация | Самодостаточная бизнес-логика. Платформы и базы достаточно для автоматизации бизнеса | [`configurations/trade`](../../configurations/trade) («Торговля и сервис»), [`internal/configuration/crypto`](../../internal/configuration/crypto) (криптопроцессинг) |
| Надстройка | Необязательная отраслевая специфика над одной конкретной базой: новые объекты, реквизиты и движения, изменение поведения базы в объявленных ею точках | [`configurations/automotive`](../../configurations/automotive) («Автобизнес» над «Торговлей и сервисом») |

`internal/configuration/none` — платформа без конфигурации.

## Одна надстройка

У тенанта не больше одной надстройки. Две отрасли в одном приложении («Автозапчасти» и «Автосервис») — это отдельная надстройка, которая их объединяет: её разработчик собирает её из пакетов обеих отраслей, сам решает их пересечения и отвечает за совместимость с базой и платформой. Поэтому надстройки не встречаются во время работы и не конфликтуют.

## Контракт

Базовая конфигурация — обычная `configuration.Configuration`. Если на ней строятся надстройки, она объявляет версию (`configuration.Versioned`, `Version()`, MAJOR.MINOR.PATCH). Её пакеты, которые импортирует надстройка, — её публичный API: добавления в них поднимают минорную версию, несовместимые изменения — мажорную.

Надстройка — `configuration.AddOn`:

```go
func (automotive) Base() configuration.Configuration { return trade.Trade() }
func (automotive) BaseVersion() string               { return "1.0.0" }
```

Платформа ([`internal/configuration/stack.go`](../../internal/configuration/stack.go)) на старте каждого процесса собирает стек (`Assemble`) и проверяет его (`CheckStack`):
- база надстройки — не надстройка;
- база объявляет версию той же мажорной и не младшей минорной, чем `BaseVersion`;
- платформа обслуживает `APIVersion` обоих слоёв.

Собранное приложение регистрирует, обслуживает (`Server`), запускает в воркере и засевает (`Seed`) сначала базу, потом надстройку. Маршрутные модули и модули проведения обоих слоёв складываются. Каталог интеграций берётся у надстройки, если она его объявляет, иначе у базы. Имя приложения — имя надстройки.

## Импорты

Закреплено тестами `internal/architecture`:
- база импортирует из платформы только `pkg/sdk` и не знает о надстройках;
- надстройка импортирует только `pkg/sdk` и пакеты своей базы;
- платформа не импортирует ни базы, ни надстройки;
- конфигурации-соседи не импортируют друг друга.

База, на которой строятся надстройки, живёт вне `internal/` (`configurations/`): надстройку из другого репозитория Go пустит к ней, а к `internal/` — нет.

## Тенант и миграции

У каждого слоя своя история миграций: `goose_db_version` платформы, `goose_db_version_<база>`, `goose_db_version_<надстройка>`. В метабазе у тенанта записаны база (`configuration`) и надстройка (`addon`) с версиями схемы каждой ([`db/meta/00003_tenant_addon.sql`](../../db/meta/00003_tenant_addon.sql)). Сервер сверяет со своими ожиданиями все три версии.

Тенанта базы можно перевести на надстройку: `<надстройка>-tenant migrate` применит её миграции и запишет её. Снять надстройку или заменить её на другую нельзя.

## Команды и фронтенд

У базы и у надстройки свои команды: `cmd/trade-*` запускают «Торговлю и сервис» одну, `cmd/automotive-*` — её с надстройкой. Манифест фронтенда надстройки называет базу:

```json
{ "register": "registerAutomotiveConfiguration", "base": "trade" }
```

`npm run configure -- automotive` собирает `app/` из базы и надстройки: база регистрируется первой, страницы базы подключаются, страница надстройки заменяет страницу базы с тем же маршрутом. `go run ./cmd/http-contracts` пишет фронтенд-файлы каждого слоя в его собственную папку.

## Этап B: реквизиты надстройки

Срез 1 сделан: надстройка объявляет свои реквизиты к **справочнику** базы или платформы.

```go
var ItemExtension = registry.Extend[item.Item, item_automotive.ItemAutomotive](Name, "Автобизнес").
	OnWrite(item_automotive.BeforeWrite).
	Search("normalized_article", item_automotive.NormalizeArticle)

func (automotive) Register(reg *registry.Registry) { reg.RegisterExtension(ItemExtension) }
```

`ItemAutomotive` — структура с тегами `db`/`json`/`meta`, как у модели. Колонка — это json-имя в snake_case: так фронтенд строит фильтры и политики полей.

**Хранение.**
- Данные лежат в таблице надстройки `<таблица справочника>__<надстройка>` (`cat_items__automotive`): одна строка на элемент, `id` — PK и FK на таблицу справочника с `ON DELETE CASCADE`.
- Таблицу создаёт миграция надстройки ([`db/configuration/automotive/00001_automotive_items.sql`](../../db/configuration/automotive/00001_automotive_items.sql)), `ALTER` таблицы базы нет.
- Платформа пишет строку сразу после строки элемента, в той же транзакции (`catalog_repo.ExtendedRepository`). Поэтому ошибка расширения — хука, проверки, ограничения таблицы — откатывает и элемент.
- У элемента, записанного до установки надстройки, строки нет, он читается с нулевыми значениями. Миграция надстройки может сразу заполнить строки существующих элементов.

**Где видны реквизиты.**
- HTTP — **плоско**, рядом с полями справочника: в запросах создания и изменения и во всех ответах (элемент, список, дерево). Не отдельным объектом, потому что форма, колонки списка, фильтры, загрузка из файла и политики полей адресуют поле по одному имени. Плоское поле надстройки работает во всех них без отдельной ветки — как в 1С, где реквизит расширения ничем не отличается от реквизита объекта.
- Столкновение имён ловит регистрация: json-имя или колонка, которые уже есть у справочника, не дают приложению стартовать. Поле, которое база добавит позже, сломает надстройку на первом же запуске, а не молча.
- Изменение без поля надстройки сохраняет его значение: в запросе все поля надстройки необязательны. Клиенты, которые не знают о надстройке, её данных не стирают.
- Метаданные и автоформа: поля добавляются к полям справочника, в группу формы надстройки (`meta:"group:…"` у поля её переопределяет). Колонки в таблице справочника у них нет, поэтому отчёты и авторизованное чтение по таблице их пока не видят.
- Список: фильтр по колонке расширения — `EXISTS` по его таблице. Отрицательные операторы — `NOT EXISTS`: элемент без строки не равен значению. `Search` добавляет к поиску списка префикс нормализованной колонки (`id IN (SELECT id FROM … WHERE col LIKE 'X%')`, под индекс `text_pattern_ops`).
- Загрузка из файла: поля надстройки предлагаются по подписям. Файл без колонки при обновлении сохраняет значение.
- Права и политики полей: права — справочника. Политики полей (FLS) действуют на колонки расширения так же, как на колонки справочника: скрытое поле не читается, не пишется и не служит фильтром или поиском, а маскированное значение, которое форма вернула пустым, сохраняется.
- Вычисляемые реквизиты (`meta:"readOnly:true"`) заполняет хук `OnWrite` надстройки — в транзакции записи, после `Validate` расширения.
- HTTP-контракты: `<Справочник><Надстройка>Request` и `Response` лежат во фронтенд-файлах надстройки, её таблица маршрутов помечает их `extends: true`. `registerHTTPRoutes` вливает их в маршруты базы, и форма базы отправляет и проверяет поля надстройки.

Справочники платформы расширяются тем же механизмом. Контрагенты тоже объявлены `Catalog`, но со своим сервисом; расширение оборачивает репозиторий сервиса (`CatalogService.WrapRepository`). Это проверяет интеграционный тест [`cmd/scaffold/extension_integration_test.go`](../../cmd/scaffold/extension_integration_test.go).

Пока не сделано:
- ссылки и формулы (`meta:"ref:…"`, `meta:"calc:…"`) в расширении — первым их ждёт справочник брендов `part_brand`;
- сортировка списка по колонке расширения, поля расширения в отчётах и глобальном поиске;
- расширение справочника с явной регистрацией (не `Catalog`) — регистрация падает с понятной ошибкой;
- реквизиты надстройки к документам и строкам документов базы;
- движения надстройки к документам базы;
- объявленные точки замены поведения базы (цена, себестоимость, заполнение на основании, статусы, нумерация).
