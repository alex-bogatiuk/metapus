# API Расширений (Extension API)

> **TL;DR:** Трехуровневая архитектура позволяет интеграторам добавлять новые сущности (справочники, документы), регистры и бизнес-логику (через Хуки) в папку `extensions/` без изменения исходного кода ядра платформы.

> **Тип:** Concept
> **Аудитория:** Developer, Integrator
> **Связанные:** [crud-pipeline.md](crud-pipeline.md)

---

## 1. Трехуровневая модель

Вместо того чтобы изменять ядро платформы (Hard Fork), Metapus использует модульную систему.

| Слой | Назначение | Кто разрабатывает | Папка |
|------|------------|-------------------|-------|
| **Core** | Движок, транзакции, права доступа | Команда Metapus | `internal/core/` |
| **Content** | Встроенные (стандартные) справочники и документы | Команда Metapus | `internal/content/` |
| **Extensions**| Кастомные клиентские сущности | Интегратор | `extensions/` |

## 2. Регистрация новых сущностей

Справочник или документ, в том числе с табличными частями, объявляется моделью и одной строкой регистрации. Модель встраивает `entity.Catalog` или `entity.Document`, объявляет поля с тегами `db`, `json`, `meta` (и `binding` для проверок запроса), возвращает `entity.Definition` и держит бизнес-методы (`Validate`, `CanPost`, источники движений):

```go
type Vehicle struct {
	entity.Catalog
	Plate   string `db:"plate" json:"plate" meta:"label:Госномер" binding:"required"`
	Mileage int    `db:"mileage" json:"mileage" meta:"label:Пробег"`
}

func (Vehicle) EntityDefinition() entity.Definition { return Definition }

func Register(reg *v1.FactoryRegistry) {
	reg.RegisterCatalog(v1.Catalog[Vehicle](metadata.Presentation{Singular: "ТС", Plural: "Транспорт"}))
}
```

`v1.Catalog` и `v1.Document` (`internal/infrastructure/http/v1/auto_registration.go`) выводят из модели и Definition всё остальное: репозиторий, сервис (генерация кода или номера, журнал событий, CEL-политики), стандартные маршруты, HTTP-контракты, metadata и права. Хуки и настройки сервиса добавляет `.Configure(func(s *domain.CatalogService[*Vehicle]) { ... })`, префикс нумерации — `.CodePrefix` / `.NumberPrefix`. Справочник со своим доменным сервисом и репозиторием подключает их через `.Service(func(deps v1.CatalogDeps) *domain.CatalogService[*Vehicle] { ... })`: регистрация по-прежнему выводит DTO, маршруты, контракты, журнал событий и политики. `.References(...)` задаёт ключи, по которым на справочник ссылаются другие модели, `.Search(...)` — колонки глобального поиска, `.ResponseName(...)` — имя ответа, если стандартное занято. Так объявлены встроенные контрагенты, валюты, договоры, организации и токены.

Запросы и ответ строятся по одному правилу (`autoShape`):

- **запись:** стандартные поля вида (справочник: `code`, `name`, у иерархического `parentId` и `isFolder`; документ: `number`, `date`, `description`), `attributes` и каждое экспортируемое поле самой модели с тегами `db` и `json`, кроме `meta:"readOnly:true"`;
- **create** — поля записи (документ — ещё `postImmediately`), **update** — они же и `version`;
- **ответ** — `id`, `version`, `deletionMark` (документ — ещё `posted`, `postedVersion`), поля записи и поля модели только для чтения.

Серверные поля базовых типов (`id`, `version`, состояние проведения) никогда не записываются; поле без колонки `db` или с `json:"-"` не попадает в контракт. Из тегов модели в запрос переносятся только `json` и `binding`, поэтому `binding:"required"` поля модели проверяется при запросе. Тело запроса читается так же строго, как типизированный DTO: неизвестное или недоступное для записи поле — ошибка 400.

Поле-ссылка (`id.ID` или `*id.ID` с `meta:"ref:<ключ>"` и json-именем на `Id`) получает в ответе представление `{id, name, code}` под именем без `Id`: `counterpartyId` → `counterparty`. Таблица берётся из зарегистрированной сущности с этим ключом или псевдонимом; неизвестный ключ — ошибка при сборке.

Табличные части документа объявляются в Definition (`Parts: []entity.Part{{Key: "goods", Field: "items"}}`), каждая — поле модели `[]Line` с json-именем `Field` и тегом `db:"-"`. Строка описывает свои колонки тегами `db` и обязательно содержит `LineID id.ID` (`db:"line_id"`) и `LineNo int` (`db:"line_no"`); таблица — `<Table>__<Key>` с `document_id` на шапку. Строки хранит `document_repo.PartStore` в той же транзакции, что и шапку, через `BaseHeaderDocumentService` (`Parts`), без SQL на каждую часть. На проводе:

- строка запроса — записываемые поля строки по тем же правилам, что у шапки (`binding` проверяется у каждой строки), и необязательный `lineId`;
- строка ответа — ещё `lineId`, `lineNo`, поля только для чтения и представления ссылок строки;
- update заменяет строки части: строка с `lineId` сохранённой строки этого документа сохраняет его и свои поля только для чтения (их заполняет сервер, например при проведении), записываемые поля берутся из запроса; остальные строки получают новый `lineId`; номера строк проставляет сервер; часть, отсутствующая в запросе, остаётся как была, пустой массив её очищает;
- строки части называются в контрактах `<Name><Field>LineRequest` / `<Name><Field>LineResponse`; таблица маршрутов фронтенда отдаёт поля строки запроса в `requestParts`; список документов строк не загружает и не отдаёт.

`Validate` и источники движений модели видят строки: документ загружается вместе с ними перед проверкой, проведением и обновлением. Фильтр списка по колонке строки задаётся как `<Field>.<колонка>` (`items.product_id`: документы, у которых есть такая строка); FLS и поиск мест использования ссылок находят строки через `Definition.Parts`. Универсальная форма (`AutoForm`, `components/shared/table-part-editor.tsx`) редактирует строки части, если `requestParts` маршрута записи её содержит: добавление, удаление, перемещение, выбор ссылок; колонки `meta:"readOnly:true"` показываются без редактора, обязательные ячейки проверяются до отправки. Часть без `requestParts` (явная регистрация, например `crypto_sweep`) показывается только для чтения.

Сущность вне правила — секреты только для записи, вычисляемые поля ответа, коллекции без своей таблицы, поле, которое можно задать лишь при изменении, или собственные маршруты — объявляет явную регистрацию (`v1.CatalogRegistrationFor[Model, Create, Update, Read]` с `Build`). Так устроены кошельки, мерчанты, блокчейн-сети, аккаунты крипто-провайдеров и интеграций, пулы, RPC-подключения и источники курсов.

Модуль подключается в общем Composition Root `extensions/register.go`; сервер, генератор контрактов и `cmd/tenant` используют этот список:
```go
myExtension.Register(factoryReg)
```

**Компоновка AutoForm.** Форму раскладывает `frontend/lib/form-layout.ts` (`planFormLayout`) по метаданным и контракту записи формы, без ручной разметки:

- **шапка** — первая строка: номер и дата документа, код и наименование справочника;
- **группы** — поля, которые пользователь заполняет. До 8 полей — одна группа без заголовка, больше — группы по видам: «Основное» (ссылки), «Суммы», «Даты», «Реквизиты», «Признаки»; вид из одного поля уходит в «Основное». Внутри группы обязательные поля идут первыми, переключатели последними. Сумма стоит в одной строке со своей валютой или токеном: по совпадению имени (`feeAmount` → `feeTokenId`), а в документе — и с первой свободной валютой или токеном;
- **длинные тексты** (`comment`, `description`, тип `text`) — на всю ширину после групп;
- **«Дополнительно»** — поля, которые форма не пишет: `meta:"readOnly:true"` или отсутствующие в запросе записи. Они показываются текстом, ссылка — полем выбора только для чтения. Обязательное поле сюда не попадает;
- **табличные части** — под формой, если часть одна и видимых полей не больше 12, иначе на закладках с числом строк вместе с «Дополнительно». Пустая обязательная ячейка открывает закладку своей части и отмечает её.

Где правила ошибаются, автор переопределяет их тегом `meta:"group:<заголовок>"`: поле уходит в именованную группу после автоматических независимо от вида и записываемости.

**Итоги по выделению.** В списке (`DataTable`) и в табличной части формы строки выделяются как в 1С. Обычный клик делает строку и колонку текущими; в табличной части он ещё и оставляет выделенной одну эту строку, а в списке не трогает флажки. Shift+клик выделяет строки от предыдущей кликнутой до текущей, Cmd/Ctrl+клик добавляет или убирает строку. В списке это та же выборка, что флажки для групповых действий. Если текущая строка выделена вместе с другими, а текущая колонка числовая, у текущей ячейки появляется подсказка `SelectionSummaryPopover`: сумма, среднее и число строк. Считается точно в десятичной арифметике (`lib/selection-summary.ts`). Деньги берутся в валюте строки, остальные числа — в единице парной колонки (валюта или токен по правилу пар из компоновки формы); значения разных единиц не складываются, у каждой свой итог. Клик по итогу копирует его без разделителей разрядов и с десятичной запятой. Пока зажаты Shift, Cmd или Ctrl, подсказка скрыта и не мешает выделять строки под ней. Колонка оверлея с собственной отрисовкой участвует в итогах, если задаёт `summary`.

**Клавиатура в списке.** Пока фокус в таблице списка (или нигде), ↑/↓, PageUp/PageDown и Home/End двигают текущую строку, а с Shift выделяют строки от якоря до неё. Якорь — строка, на которую перешли последней без Shift. ←/→ меняют текущую колонку, Enter открывает текущую строку. Строка и ячейка прокручиваются в видимую область. Клавиши в полях ввода, меню и диалогах таблица не перехватывает. Расчёт целевой строки — `rowMoveTarget` и `rowRange` в `lib/row-selection.ts`. Когда меню или диалог страницы списка закрывается и возвращает фокус на кнопку панели, фокус переходит на текущую строку таблицы, чтобы клавиши продолжали работать. Страница отмечает свой корень атрибутом `data-list-page`; фокус, отданный полю ввода или элементу вне страницы, остаётся на месте.

**Табличные части как в 1С.** Пользовательская настройка вида `tablePartCellMode` («Табличные части как в 1С» в профиле) переключает `TablePartEditor` в режим ячеек. Ячейки показывают значения текстом, клик делает ячейку текущей. Двойной клик, Enter или F2 открывают её для правки со всем значением выделенным. Enter или Tab завершают правку, Escape её отменяет, а в строке, только что добавленной через Insert, убирает строку. Флажок переключается сразу, пробелом или двойным кликом. Пока фокус на таблице: стрелки, PageUp/PageDown, Home/End и Tab двигают текущую ячейку, Shift расширяет выделение, Ctrl/Cmd+A выделяет все строки, Escape сворачивает выделение до текущей, Ctrl/Cmd+C копирует ячейку или выделенные строки (через табуляцию), Delete или Cmd/Ctrl+Backspace удаляют выделенные строки, Insert добавляет строку, F9 копирует выделенные строки ниже последней, Ctrl/Cmd+Shift+↑/↓ двигают текущую строку. Копия строки — новая строка: в неё переносятся только поля, которые принимает запрос (`copyRows`). Обработанные клавиши дальше не всплывают, поэтому горячие клавиши формы и приложения их не видят. На краю строки Tab выводит фокус из таблицы. Команды над строками собраны, как в 1С, в командной панели между заголовком и таблицей: «Добавить», «Скопировать», «Вверх», «Вниз», «Удалить» и справа положение («Строка 3 из 5», «Выделено 2 из 5»). Они работают в обоих режимах и действуют на выделенные строки, а если текущая строка вне выделения — на неё одну. Выделенные строки перемещаются блоком (`moveRows`), на краю команда неактивна. Кнопки панели не забирают фокус, поэтому клавиатура остаётся в таблице или в открытой ячейке. Без настройки табличная часть работает как раньше: поля ввода в ячейках всегда открыты.

**Frontend Auto-Discovery:**
Платформа генерирует UI для расширений автоматически! Фронтенд получает `/api/v1/meta/entities` и использует generic routes `[routePrefix]` для списка и AutoForm. Запросы/ответы должны быть зарегистрированы в HTTP contracts registry: metadata не разрешает незарегистрированный URL или дополнительное writable поле. Новые сущности автоматически появляются в разделе расширений меню и в палитре команд у пользователей с их правом чтения: `/meta/entities` отдаёт `readPermission` сущности, а `lib/navigation-access` скрывает пункт без него (форма `/new` требует права `create`; пункт с явным `permission` проверяется по нему); custom forms и особое размещение подключаются через frontend registry/navigation. Подробности — [новый справочник](../howto/new-entity.md).

## 3. Точки расширения

Кроме создания новых сущностей, Extension API позволяет "вклиниваться" в стандартные:

1. **Хуки (Hooks):** Инъекция кастомной логики в системные документы.
   ```go
   invoiceService.Hooks().OnBeforeCreate(func(ctx, doc) error { ... })
   ```
2. **Новые Регистры:** Интегратор может написать свой `RegisterVisitor` и `RegisterRecorder`, чтобы документы, реализующие нужные source-интерфейсы начали двигать новые кастомные регистры. Регистры конфигурации подключаются модулем `posting.Module` через `RouterConfig.PostingModules`: модуль добавляет visitors, recorders и проверки в движок и возвращает `MovementProvider` для отчёта о движениях документа. Пример — `cryptoregisters.Registers`.
3. **Атрибуты (JSONB):** У каждой сущности есть поле `attributes` для произвольных данных интегратора. Схемы, валидации, фильтрации и колонок для них нет; типизированное поле добавляется в Go-модель сущности.
4. **CEL Политики:** Написание кастомных правил блокировок (например, запрет проведения документов с суммой > 1 млн) в виде конфигурации через CEL (Common Expression Language), без перекомпиляции Go.

## 4. Модули конфигурации

Конфигурация (сейчас — криптопроцессинг) подключается к платформе модулями, а не правками ядра:

| Точка расширения | Что даёт конфигурация | Пример в Metapus |
|---|---|---|
| `posting.Module` | регистры, visitors/recorders и проверки проведения; возвращает `MovementProvider` | `infrastructure/crypto/cryptoregisters` |
| `v1.RouteModule` (`RouterConfig.RouteModules`) | маршруты на группах из `v1.RouteContext`: `Root`, `API`, `Protected`, `System`; свои зависимости модуль хранит сам | `infrastructure/http/cryptohttp` |
| `auth.WithAccessScopeProvider` | объектные права сессии в claim `scp` | `merchant.NewPortalAccessScopes` |
| `middleware.WithCommandScope` | владелец ключей идемпотентных команд (например, партнёр по API-ключу) | `cryptomiddleware.WithMerchant`, `MerchantPortal` |
| `content.Services` | сервисы конфигурации для регистраций документов вне `v1.DocumentDeps` | ссылки checkout, подписанты согласований |
| `integrations.Catalog` | назначения и провайдеры интеграций конфигурации рядом с платформенными (CoinGecko, Telegram, SMTP). Каталог неизменяем, собирается один раз и передаётся явно: сервисам аккаунтов и пулов, выбору аккаунтов (`integration_repo.NewRuntime`), `RouterConfig.IntegrationCatalog`; HTTP-профили — реестром `profiles.New(...)`. Список провайдеров в БД задаёт миграция конфигурации | `cryptointegrations.Catalog()`, `cryptoprofiles.Registry()` |
| `integrations.PoolConsumer` | справочник, читающий аккаунты через пулы интеграций: пул нельзя удалить или сменить ему провайдера, пока потребитель им пользуется; состав пула и новые ключи аккаунта проверяются по его требованиям. Конфигурация создаёт репозитории аккаунтов и пулов со своими потребителями | `crypto_integration_repo.RPCPoolConsumer` |
| `entity.MovementColumnDef.RefEntity` | колонка-ссылка движения регистра называет сущность, на которую ссылается; по ней разрешаются представление и ссылка `/catalogs|documents/{route}/{id}`. Колонка без `RefEntity` не показывается | колонки регистров `crypto_*` |
| `platform.MovementSourceProvider` | для документа с движениями: какие его поля раскрывают каждую колонку движения. При FLS-политике на документ колонка видна, только если объявлена и все перечисленные поля читаемы; пустой список — колонка-константа | `content/movement_sources.go` |
| `db/configuration/<имя>/` | миграции конфигурации: её таблицы, права и FLS её сущностей, ограничения её правил на таблицах платформы. Они в общей последовательности версий с платформенными `db/migrations/` и применяются одним источником `dbassets.TenantMigrations()` | `db/configuration/crypto/` |
| `spec.Bundle` | контракты HTTP конфигурации; генератор пишет их в её собственные файлы `frontend/configuration/<имя>/{types,lib}/generated/`, а типы платформы импортирует из платформенных файлов (`contracts.GenerateOn`, `contracts.GenerateRoutesOn`) | `content.CryptoHTTPContractBundles`, `content.HTTPArtifacts` |

Граница проверяется тестами в `internal/architecture`:

- `configuration_boundary_test.go`: платформенный пакет не импортирует пакет конфигурации; список исключений пуст и должен таким остаться;
- `configuration_storage_test.go`: строковые литералы платформенного кода не называют таблицы из миграций конфигурации (`db/configuration/*`), а тесты платформы не импортируют конфигурацию; оба списка исключений пусты. Проверки собранного приложения (все HTTP-контракты, актуальность сгенерированных файлов, наборы отчётов конфигурации) лежат в `internal/content`, проверки поведения конфигурации — в её пакетах.

Во фронтенде код конфигурации лежит в `frontend/configuration/<имя>/` (`components`, `lib`, `hooks`, `types`, `stores` с той же структурой, что у платформы), платформенный — в `frontend/components`, `lib`, `hooks`, `stores`, `types`. Страницы и layout конфигурации лежат в `frontend/configuration/<имя>/pages/` по структуре маршрутов. `frontend/app/` — точка сборки: маршрут конфигурации в нём — однострочная обёртка `export { default } from "@/configuration/<имя>/pages/…"`, которую требует Next.js. Тест `frontend/tests/unit/configuration-boundary.spec.ts` проверяет, что:

- платформенные файлы не импортируют `configuration/`, и список исключений пуст;
- платформенный код и маршруты `app/` не используют словарь конфигурации (crypto, merchant, portal, wallet и т. п.), кроме путей модулей;
- `app/` обращается к конфигурации только через такие обёртки и `app/configuration.ts`.

Конфигурация подключает свои части при старте: `frontend/app/configuration.ts` вызывает `registerCryptoConfiguration()`, его импортируют первыми клиентский layout `app/(main)` и страница дашборда.

| Точка расширения фронтенда | Что даёт конфигурация | Пример |
|---|---|---|
| `registerEntityOverlays` (`lib/entity-registry-defaults`) | колонки, видимость, фильтры, форма и список для сущностей из metadata | `configuration/crypto/lib/entity-overlays.ts` |
| `registerWidget` (`lib/widget-registry`) | виджет дашборда со своей схемой настроек (`configSchema`) и редактором (`configEditor`) | `configuration/crypto/lib/widgets.tsx` |
| `registerDefaultDashboard` (`lib/dashboard-layout`) | дашборд пользователя по умолчанию | там же |
| `detailContent`, `renderField` в overlay сущности | панели под формой существующей записи и свои редакторы полей на generic-страницах `[routePrefix]/[id]` | `configuration/crypto/components/detail-panels.tsx` |
| `registerNavigation` (`lib/navigation`) | группы разделов меню (в существующую группу или после указанной), системные ссылки, пункты палитры команд; у пункта может быть `permission` | `configuration/crypto/lib/navigation.ts` |
| `registerRouteEntities`, `registerIcons`, `registerRouteLabels` | ключ сущности, иконка и заголовок вкладки по URL до загрузки metadata | там же |
| `registerWorkspace` (`lib/access`) | отдельный интерфейс для пользователей без доступа к ERP; `landingPath(user)` выбирает его после входа | `configuration/crypto/lib/access.ts` (портал) |
| `createScopedClient(scope)` (`lib/api`) | клиент своей HTTP-области `/<scope>/v1` с общей сессией, проверкой контрактов и идемпотентностью | `configuration/crypto/lib/api/portal.ts` |
| `registerSecurityDimension`, `registerProfilePreset`, `registerAffinityRule`, `registerResourceLabels` (`lib/security-registry`) | RLS-измерение с поиском значений, шаблоны профилей безопасности, подсказки ролей, названия ресурсов прав | `configuration/crypto/lib/security.ts` |
| `registerSettingsPage` (`lib/settings-registry`), `registerAdminSection` (`lib/admin-registry`) | свои страницы в «Настройках» и разделы в «Управлении» | `configuration/crypto/lib/settings.tsx`, `lib/admin.ts` |
| `registerStatusColors`, `registerWorkerJobs` | цвет статусов и фильтры журнала задач воркера | `configuration/crypto/lib/labels.ts` |
| собственный API-клиент | её эндпоинты; платформенный `@/lib/api` содержит только платформенные | `configuration/crypto/lib/api` (`cryptoApi`) |

Регистрации выполняются при загрузке модуля `app/configuration.ts`, поэтому платформа читает реестры при рендере, а не при загрузке своих модулей. Хранилища конфигурации, сохраняемые в `localStorage`, называются с префиксом `SCOPED_STORAGE_PREFIX` (`metapus-scoped-`): платформа очищает их при смене пользователя, даже если модуль ещё не загружен.

Печатные формы документ конфигурации объявляет через `v1.PrintFormsProvider`; типы областей команд (`command.Metadata.ScopeType`) и маршрутов контрактов — открытые идентификаторы, конфигурация добавляет свои (`merchant`, `portal`) без правок ядра. Состояние раскрытых секций интерфейса хранится в `interface.expandedSections` под ключом, который выбирает UI.

Коды ошибок конфигурации объявляются рядом с её доменом и собираются из `apperror.AppError`; `core/apperror` хранит только платформенные коды. Например, `WALLET_POOL_EXHAUSTED` объявлен в `catalogs/wallet`, `CRYPTO_NETWORK_UNAVAILABLE` в `catalogs/blockchain_network`. Подсказку `details.retryAfterSeconds` любой ошибки `ErrorHandler` выставляет в заголовок `Retry-After`.

## 5. Scaffold CLI

Для ускорения разработки расширений используется встроенный кодогенератор:
```bash
go run cmd/scaffold/main.go --name waybill --type document
```
Генератор создаёт модуль из двух Go-файлов — `model.go` (Definition и модель) и `register.go` (одна строка `v1.Catalog`/`v1.Document`) — и миграцию с актуальными CDC triggers. DTO, репозиторий, сервис и регистрация выводятся из модели (раздел 2). Права модуля миграция не объявляет: `cmd/tenant migrate` выводит их из регистрации и выдаёт роли admin. Миграция пишется в `db/configuration/<name>/` с версией 10000+: оттуда она встраивается в бинарники и применяется вместе с платформенными. Документ создаётся без табличных частей; `--parts goods,services` добавляет их: `entity.Part` в Definition, поле и тип строки в модели, таблицы `<Table>__<key>` в миграции. `--hierarchical` включает папки и проверки иерархии справочника; без флага справочник плоский.

Общее `entity.Definition` связывает identity, таблицу, маршрут и hierarchy. `contracts/spec.Entity` выводит стандартные HTTP-контракты из Definition и конкретных DTO, `spec.EntityOf` — из типов, построенных во время выполнения (декларативная регистрация). После добавления модуля в `extensions/register.go` выполните `go run ./cmd/http-contracts`; отдельные правки registry/routes для расширения не нужны. Права других ролей, бизнес-поля, локализация, движения и новый worker workflow требуют явной настройки.

Модули `extensions/` компилируются внутри Metapus. Публичный внешний SDK в `pkg/extension` пока ограничен версией API; не используйте его как готовый фасад регистрации.

## 6. Единый контракт встроенных сущностей и расширений

Все встроенные справочники и документы предоставляют domain `Definition`. Модель реализует `EntityDefinition()`; generic `EntityRegistration[Model]` выводит identity и metadata, `CatalogRegistrationFor[Model,Create,Update,Read]` также выводит стандартные transport contracts. Нулевое значение регистрации работоспособно: передавать Definition вручную в struct literal не требуется.

Factory contracts требуют Definition и HTTP bundle. Стандартные DTO и маршруты codegen получает из того же registry, что и сервер. Разрешённые document capabilities ограничивают набор сгенерированных маршрутов; custom команды и специальные detail projections объявляются у владельца документа.

Catalog service и repository читают hierarchy из Definition, включая type, folder restrictions и max depth. Глобальный реестр hierarchy удалён; прямые repository writes используют ту же политику, что и service. Для отдельного тестового ограничения передайте копию Definition с нужной Hierarchy.

## Extension API 2.0

Добавлены обязательные Definition и HTTPContracts у factory registrations. CatalogServiceConfig принимает Definition вместо строкового EntityName; глобальные GetCatalogMeta/RegisterCatalogMeta удалены. Внешний модуль на прежнем API должен перейти на EntityDefinition, typed registration и Definition-based repository/service constructors. Новые scaffold-модули сразу используют API 2.0.
