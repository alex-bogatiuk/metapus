# API Расширений (Extension API)

> **TL;DR:** Трехуровневая архитектура позволяет интеграторам добавлять новые сущности (справочники, документы), регистры и бизнес-логику (через Хуки) в папку `extensions/` без изменения исходного кода ядра платформы.

> **Тип:** Concept
> **Аудитория:** Developer, Integrator
> **Связанные:** [crud-pipeline.md](crud-pipeline.md)

---

## 1. Трехуровневая модель

Вместо того чтобы изменять ядро платформы (Hard Fork), Metapus использует модульную систему.

| Слой | Назначение | Кто разрабатывает | Папка |
|------|------------|-------------------|-------|
| **Core** | Движок, транзакции, права доступа | Команда Metapus | `internal/core/` |
| **Content** | Общие справочники платформы и отраслевые конфигурации (сейчас — криптопроцессинг) | Команда Metapus | `internal/platformcontent/`, `internal/configuration/crypto/content/` |
| **Extensions**| Кастомные клиентские сущности | Интегратор | `extensions/` |

## 2. Регистрация новых сущностей

Справочник или документ, в том числе с табличными частями, объявляется моделью и одной строкой регистрации. Модель встраивает `entity.Catalog` или `entity.Document`, объявляет поля с тегами `db`, `json`, `meta` (и `binding` для проверок запроса), возвращает `entity.Definition` и держит бизнес-методы (`Validate`, `CanPost`, источники движений):

```go
type Vehicle struct {
	entity.Catalog
	Plate   string `db:"plate" json:"plate" meta:"label:Госномер" binding:"required"`
	Mileage int    `db:"mileage" json:"mileage" meta:"label:Пробег"`
}

func (Vehicle) EntityDefinition() entity.Definition { return Definition }

func Register(reg *v1.FactoryRegistry) {
	reg.RegisterCatalog(v1.Catalog[Vehicle](metadata.Presentation{Singular: "ТС", Plural: "Транспорт"}))
}
```

`v1.Catalog` и `v1.Document` (`internal/infrastructure/http/v1/auto_registration.go`) выводят из модели и Definition всё остальное: репозиторий, сервис (генерация кода или номера, журнал событий, CEL-политики), стандартные маршруты, HTTP-контракты, metadata и права. Хуки и настройки сервиса добавляет `.Configure(func(s *domain.CatalogService[*Vehicle]) { ... })`. Правило кода справочника объявляет `Definition.Code`, префикс номеров документа — `Definition.Number` ([numerator.md](numerator.md)); его исполняет `CatalogService`, поэтому оно действует и для справочника с собственным сервисом. Справочник со своим доменным сервисом и репозиторием подключает их через `.Service(func(deps v1.CatalogDeps) *domain.CatalogService[*Vehicle] { ... })`: регистрация по-прежнему выводит DTO, маршруты, контракты, журнал событий и политики. `.References(...)` задаёт ключи, по которым на справочник ссылаются другие модели, `.Search(...)` — колонки глобального поиска, `.ResponseName(...)` — имя ответа, если стандартное занято. Так объявлены встроенные контрагенты, валюты, договоры, организации и токены.

Запросы и ответ строятся по одному правилу (`autoShape`):

- **запись:** стандартные поля вида (справочник: `code`, `name`, у иерархического `parentId` и `isFolder`; документ: `number`, `date`, `description`), `attributes` и каждое экспортируемое поле самой модели с тегами `db` и `json`, кроме `meta:"readOnly:true"`;
- **create** — поля записи (документ — ещё `postImmediately`), **update** — они же и `version`;
- **ответ** — `id`, `version`, `deletionMark` (документ — ещё `posted`, `postedVersion`), поля записи и поля модели только для чтения.

Серверные поля базовых типов (`id`, `version`, состояние проведения) никогда не записываются; поле без колонки `db` или с `json:"-"` не попадает в контракт. Из тегов модели в запрос переносятся только `json` и `binding`, поэтому `binding:"required"` поля модели проверяется при запросе. Тело запроса читается так же строго, как типизированный DTO: неизвестное или недоступное для записи поле — ошибка 400.

Поле-ссылка (`id.ID` или `*id.ID` с `meta:"ref:<ключ>"` и json-именем на `Id`) получает в ответе представление `{id, name, code}` под именем без `Id`: `counterpartyId` → `counterparty`. Таблица берётся из зарегистрированной сущности с этим ключом или псевдонимом; неизвестный ключ — ошибка при сборке.

Табличные части документа объявляются в Definition (`Parts: []entity.Part{{Key: "goods", Field: "items"}}`), каждая — поле модели `[]Line` с json-именем `Field` и тегом `db:"-"`. Строка описывает свои колонки тегами `db` и обязательно содержит `LineID id.ID` (`db:"line_id"`) и `LineNo int` (`db:"line_no"`); таблица — `<Table>__<Key>` с `document_id` на шапку. Строки хранит `document_repo.PartStore` в той же транзакции, что и шапку, через `BaseHeaderDocumentService` (`Parts`), без SQL на каждую часть. На проводе:

- строка запроса — записываемые поля строки по тем же правилам, что у шапки (`binding` проверяется у каждой строки), и необязательный `lineId`;
- строка ответа — ещё `lineId`, `lineNo`, поля только для чтения и представления ссылок строки;
- update заменяет строки части: строка с `lineId` сохранённой строки этого документа сохраняет его и свои поля только для чтения (их заполняет сервер, например при проведении), записываемые поля берутся из запроса; остальные строки получают новый `lineId`; номера строк проставляет сервер; часть, отсутствующая в запросе, остаётся как была, пустой массив её очищает;
- строки части называются в контрактах `<Name><Field>LineRequest` / `<Name><Field>LineResponse`; таблица маршрутов фронтенда отдаёт поля строки запроса в `requestParts`; список документов строк не загружает и не отдаёт.

`Validate` и источники движений модели видят строки: документ загружается вместе с ними перед проверкой, проведением и обновлением. Фильтр списка по колонке строки задаётся как `<Field>.<колонка>` (`items.product_id`: документы, у которых есть такая строка); FLS и поиск мест использования ссылок находят строки через `Definition.Parts`. Универсальная форма (`AutoForm`, `components/shared/table-part-editor.tsx`) редактирует строки части, если `requestParts` маршрута записи её содержит: добавление, удаление, перемещение, выбор ссылок; колонки `meta:"readOnly:true"` показываются без редактора, обязательные ячейки проверяются до отправки. Часть без `requestParts` (явная регистрация, например `crypto_sweep`) показывается только для чтения.

Сущность вне правила — секреты только для записи, вычисляемые поля ответа, коллекции без своей таблицы, поле, которое можно задать лишь при изменении, или собственные маршруты — объявляет явную регистрацию (`v1.CatalogRegistrationFor[Model, Create, Update, Read]` с `Build`). Так устроены кошельки, мерчанты, блокчейн-сети, аккаунты крипто-провайдеров и интеграций, пулы, RPC-подключения и источники курсов.

Модуль подключается в общем Composition Root `extensions/register.go`; сервер, генератор контрактов и команды тенантов используют этот список:
```go
myExtension.Register(factoryReg)
```

**Компоновка AutoForm.** Форму раскладывает `frontend/lib/form-layout.ts` (`planFormLayout`) по метаданным и контракту записи формы, без ручной разметки:

- **шапка** — первая строка: номер и дата документа, код и наименование справочника;
- **группы** — поля, которые пользователь заполняет. До 8 полей — одна группа без заголовка, больше — группы по видам: «Основное» (ссылки), «Суммы», «Даты», «Реквизиты», «Признаки»; вид из одного поля уходит в «Основное». Внутри группы обязательные поля идут первыми, переключатели последними. Сумма стоит в одной строке со своей валютой или токеном: по совпадению имени (`feeAmount` → `feeTokenId`), а в документе — и с первой свободной валютой или токеном;
- **длинные тексты** (`comment`, `description`, тип `text`) — на всю ширину после групп;
- **«Дополнительно»** — поля, которые форма не пишет: `meta:"readOnly:true"` или отсутствующие в запросе записи. Они показываются текстом, ссылка — полем выбора только для чтения. Обязательное поле сюда не попадает;
- **табличные части** — под формой, если часть одна и видимых полей не больше 12, иначе на закладках с числом строк вместе с «Дополнительно». Пустая обязательная ячейка открывает закладку своей части и отмечает её.

Где правила ошибаются, автор переопределяет их тегом `meta:"group:<заголовок>"`: поле уходит в именованную группу после автоматических независимо от вида и записываемости.

**Итоги по выделению.** В списке (`DataTable`) и в табличной части формы строки выделяются как в 1С. Обычный клик делает строку и колонку текущими; в табличной части он ещё и оставляет выделенной одну эту строку, а в списке не трогает флажки. Shift+клик выделяет строки от предыдущей кликнутой до текущей, Cmd/Ctrl+клик добавляет или убирает строку. В списке это та же выборка, что флажки для групповых действий. Если текущая строка выделена вместе с другими, а текущая колонка числовая, у текущей ячейки появляется подсказка `SelectionSummaryPopover`: сумма, среднее и число строк. Считается точно в десятичной арифметике (`lib/selection-summary.ts`). Деньги берутся в валюте строки, остальные числа — в единице парной колонки (валюта или токен по правилу пар из компоновки формы); значения разных единиц не складываются, у каждой свой итог. Клик по итогу копирует его без разделителей разрядов и с десятичной запятой. Пока зажаты Shift, Cmd или Ctrl, подсказка скрыта и не мешает выделять строки под ней. Колонка оверлея с собственной отрисовкой участвует в итогах, если задаёт `summary`.

**Клавиатура в списке.** Пока фокус в таблице списка (или нигде), ↑/↓, PageUp/PageDown и Home/End двигают текущую строку, а с Shift выделяют строки от якоря до неё. Якорь — строка, на которую перешли последней без Shift. ←/→ меняют текущую колонку, Enter открывает текущую строку. Строка и ячейка прокручиваются в видимую область. Клавиши в полях ввода, меню и диалогах таблица не перехватывает. Расчёт целевой строки — `rowMoveTarget` и `rowRange` в `lib/row-selection.ts`. Когда меню или диалог страницы списка закрывается и возвращает фокус на кнопку панели, фокус переходит на текущую строку таблицы, чтобы клавиши продолжали работать. Страница отмечает свой корень атрибутом `data-list-page`; фокус, отданный полю ввода или элементу вне страницы, остаётся на месте.

**Расчётные поля** (как пересчёт суммы строки в 1С). Числовое поле документа или строки его табличной части объявляется формулой: `meta:"calc:quantity*price"`. Формула — арифметика над JSON-именами числовых полей той же структуры: числа, `+ - * /`, скобки, унарный минус.
- **Сервер.** Поле только для чтения: в запросе его нет (строгий запрос с ним отклоняется), в ответе оно есть. Сервер вычисляет его после применения запроса при каждом создании и изменении документа, в шапке и в каждой строке (`v1/auto_calc.go`, разбор — `internal/core/formula`). У сохранённой строки, чьи количество или цена изменились, сумма пересчитывается.
- **Значения в формуле — в единицах поля.** Деньги (`MinorUnits`) — в минимальных единицах, поэтому `quantity*price` остаётся в валюте цены и курс не нужен. `Quantity` — в своём десятичном значении, целые и `decimal.Decimal` — как есть, пустой указатель — ноль.
- **Точность.** Арифметика точная, частное округляется до 16 знаков, деление на ноль даёт ноль, чтобы пустое количество не блокировало запись. Результат округляется половиной от нуля до масштаба поля: деньги и целые до целого, `Quantity` и `decimal` до четырёх знаков.
- **Итог документа.** Формула шапки может просуммировать колонку табличной части: `meta:"calc:sum(items.amount)"`, в том числе вместе с другой арифметикой (`sum(items.amount)-discount`). `sum` — единственная функция, её аргумент — `<JSON-имя части>.<JSON-имя числовой колонки строки>`. Строки считаются раньше шапки, поэтому итог видит уже рассчитанные суммы строк. Неизвестная часть или нечисловая колонка — ошибка регистрации. В форме итог шапки пересчитывается при любом изменении строк, а в подсказке показан как «Σ «Товары: Сумма»».
- **Порядок.** Формула может читать другое расчётное поле: поля считаются в порядке зависимостей.
- **Проверки при регистрации.** Цикл, неизвестное или нечисловое имя, нечисловая цель и формула в справочнике — ошибки регистрации. Переполнение результата — ошибка проверки с названием поля.
- **Форма.** Метаданные передают формулу в `calc`. `lib/formula.ts` повторяет те же правила, и форма пересчитывает поле на лету: табличная часть — при любом изменении строк, шапка — при изменении полей. Тип значения сохраняется: деньги и `decimal` остаются строками, как в протоколе. В табличной части у такой колонки значок ƒ с формулой в подсказке, а значение читается как обычные данные, не приглушённым. В шапке расчётное поле остаётся в своей группе текстом, а не уходит в «Дополнительно».
- **Деньги в валюте документа.** Деньги хранятся и передаются в минимальных единицах, а форма показывает и принимает их в основных единицах валюты документа: «1 999,99», с кодом валюты в заголовке колонки и в поле шапки (`useDocumentCurrency`).
  - **Какая валюта.** Берётся валюта, указанная в шапке (`currencyId` или первая ссылка на валюту). Если её нет или она не выбрана — базовая валюта системы (`cat_currencies.is_base`, единственная). Если не удаётся прочитать ни ту, ни другую, остаются минимальные единицы.
  - **Ячейки табличной части.** Работают в основных единицах вместе с калькулятором. Лишние знаки результата округляются половиной от нуля, как сервер округляет расчётные деньги. Вставка из Excel читает суммы в основных единицах. Подвал и итоги выделения считают в валюте документа.
  - **Поле шапки.** Принимает сумму точно: лишние знаки после запятой отклоняются с сообщением, а не округляются.
  - **Смена валюты.** Сохранённое число минимальных единиц не меняется, меняется только его прочтение: 1999 копеек в иенах читается как 1999 иен.

**Табличные части как в 1С.** Пользовательская настройка вида `tablePartCellMode` («Табличные части как в 1С» в профиле) переключает `TablePartEditor` в режим ячеек. Ячейки показывают значения текстом, клик делает ячейку текущей. Двойной клик, Enter или F2 открывают её для правки со всем значением выделенным. Enter или Tab завершают правку, Escape её отменяет, а в строке, только что добавленной через Insert, убирает строку. Флажок переключается сразу, пробелом или двойным кликом. Пока фокус на таблице: стрелки, PageUp/PageDown, Home/End и Tab двигают текущую ячейку, Shift расширяет выделение, Ctrl/Cmd+A выделяет все строки, Escape сворачивает выделение до текущей, Ctrl/Cmd+C копирует ячейку или выделенные строки (через табуляцию), Delete или Cmd/Ctrl+Backspace удаляют выделенные строки, Insert добавляет строку, F9 копирует выделенные строки ниже последней, Ctrl/Cmd+Shift+↑/↓ двигают текущую строку. Копия строки — новая строка: в неё переносятся только поля, которые принимает запрос (`copyRows`). Обработанные клавиши дальше не всплывают, поэтому горячие клавиши формы и приложения их не видят. На краю строки Tab выводит фокус из таблицы. Команды над строками собраны, как в 1С, в командной панели между заголовком и таблицей: «Добавить», «Скопировать», «Вверх», «Вниз», «Удалить» и справа положение («Строка 3 из 5», «Выделено 2 из 5»). Они работают в обоих режимах и действуют на выделенные строки, а если текущая строка вне выделения — на неё одну. Выделенные строки перемещаются блоком (`moveRows`), на краю команда неактивна. Кнопки панели не забирают фокус, поэтому клавиатура остаётся в таблице или в открытой ячейке.

**Оформление табличной части.**
- **Строка ввода.** У записываемой части под последней строкой всегда есть пустая строка с «+», как в Excel и Airtable. Начал вводить в любую её ячейку — она становится строкой, ниже появляется новая пустая. Новая строка сохраняет ключ строки ввода, поэтому ячейка, в которой печатают, не теряет фокус. В режиме ячеек на строку ввода можно перейти стрелками, а Escape в ней отменяет добавление.
- **Ввод с клавиатуры.** В режиме ячеек символ, набранный на выбранной ячейке, открывает её и заменяет значение. Ссылочная ячейка при этом открывает выбор с набранным в поиске. Символы, набранные до того, как поле получило фокус, не теряются. Числовые колонки (целые и дробные, кроме денег) редактируются собственным полем таблицы: оно принимает «1 234,5», выражения (`500*4`, `1,5*(2+3)`, калькулятор из `lib/calc-engine.ts`) и изменение текущего значения (`+5`, `*2`, `/4`), а считает на Enter, Tab или уходе из ячейки (`evaluateNumberInput`). Целые округляются, обычные числа применяются сразу, и подвал следует за вводом.
- **Заполнить** (как «Заполнить» в 1С, Ctrl+D в Excel): значение текущей ячейки переходит в ту же колонку остальных выделенных строк, ссылка вместе с её представлением (`fillColumn`).
- **Вставка из Excel и Google Таблиц.** Ctrl/Cmd+V с фокусом в ячейке или на таблице разбирает табличный текст (`parseClipboardGrid`, с кавычками и переносами внутри ячеек) и кладёт его с текущей ячейки, как это делает Excel. Строки сверх конца таблицы добавляются, заполняются только записываемые колонки, пустые ячейки вставки ничего не меняют. Значения разбираются по типу колонки: числа «1 234,5», даты «31.12.2026», да/нет, перечисления по названию. Ссылки ищутся в справочнике по коду или наименованию, а если результат один — берётся он. Нераспознанное остаётся как было, и уведомление его перечисляет. Одиночное значение, вставленное в поле, остаётся обычной вставкой в поле.
- **Отмена.** Каждое изменение строк запоминается: добавление, удаление, копирование, перемещение, подбор, заполнение, вставка и правка ячеек (правки одной ячейки подряд считаются одним шагом). Ctrl/Cmd+Z в режиме ячеек и кнопка «Отменить» на панели возвращают шаг назад. Удаление, заполнение, вставка и подбор показывают уведомление с кнопкой «Вернуть». Запись документа начинает историю заново.
- **Подвал «Итого»** (как «Подвал» в 1С) суммирует по всем строкам колонки, чьи значения складываются: числа и деньги, кроме цен, ставок, процентов и коэффициентов (`isSummableField`). Разные валюты и токены суммируются раздельно. Клик по итогу копирует его для калькулятора.
- **Размер и компоновка.** Табличные части занимают всю ширину формы, а поля шапки и «Дополнительно» остаются колонкой 768 px. Строки 32 px (28 px в компактном режиме). Поля в ячейках обычного режима без рамки, пока на них не навели или не сфокусировались, а значки поля выбора тоже появляются только при наведении. Высокая таблица прокручивается внутри своей рамки, как табличная часть в 1С: заголовок колонок и подвал «Итого» прилипают к краям, а при горизонтальной прокрутке на месте остаются № и первая колонка (обычно позиция). Строки непрозрачные, чтобы закреплённые ячейки закрывали то, что уезжает под них. Двойной клик по границе колонки подгоняет её ширину под самое длинное значение: текст меряется в своём шрифте, к нему прибавляется обвязка ячейки. Область прокрутки формы не растягивается под широкую таблицу, поэтому вбок прокручивается таблица, а не страница.
- **Колонки.** Начальная ширина зависит от типа: ссылки и строки шире, числа и флажки уже. Числа выровнены вправо, в том числе в полях ввода. Ширину колонки можно менять перетаскиванием, и она запоминается в настройках пользователя под ключом `<Сущность>.<часть>` — форма передаёт его в `widthsKey`. Последняя колонка, как в 1С, забирает оставшееся место, остальные держат ровно заданную ширину.
- **Строки.** У текущей строки полоса слева, как в списках, у выделенных — приглушённая полоса. В режиме ячеек незаполненная обязательная ячейка подчёркнута красным пунктиром, как в 1С.
- **Ошибка записи.** Если при записи найдена пустая обязательная ячейка, `LineInputError` называет строку и колонку. Форма открывает вкладку части и передаёт ячейку в `focusRequest`: ячейка становится текущей и обводится красным, пока её не заполнят. В обычном режиме фокус ставится в её поле, в режиме ячеек ячейка сразу открывается для правки.
- **Контекстное меню строки** по правому клику повторяет команды панели и добавляет «Копировать в буфер». Строка вне выделения перед этим становится единственной выделенной. Когда в ячейках поля ввода, меню открывается только на №, чтобы у полей оставалось меню браузера (вставка, орфография).

**Работа с длинной табличной частью.**
- **Незаполненное по ходу ввода.** Пустая обязательная ячейка, которую пользователь может заполнить, помечена красным пунктиром в обоих режимах, с подсказкой «Заполните «…»» (`missingCells`). Счётчик «Не заполнено: N» на панели команд ведёт к следующей такой ячейке, а с полями ввода ставит в неё курсор.
- **Поиск** (Ctrl/Cmd+F в таблице или из ячейки, кнопка с лупой): ищет по показанному тексту ячеек без учёта регистра (`findCells`). Совпадения подсвечены, текущее ярче, счётчик «2 из 5». Enter или ↓ — следующее, Shift+Enter или ↑ — предыдущее, Escape закрывает. Текущим становится найденная ячейка, а клавиатура остаётся в поле поиска. Подсветка — оттенок поверх фона ячейки (`td[data-match]` в `globals.css`), поэтому закреплённые колонки свой фон сохраняют.
- **Упорядочить** (меню на панели, как «Упорядочить» в 1С): переставляет сами строки документа, а не их вид (`sortRows`). Числа и деньги — по значению, текст и ссылки — по показанному, пустые — в конце, равные сохраняют порядок. Отменяется через «Вернуть».
- **Колонки** (меню на панели): какие колонки показывать в таблице, запоминается для пользователя по ключу `<Сущность>.<часть>__columns`. Обязательную колонку скрыть нельзя, чтобы её пропуски были видны. Скрытые поля остаются в панели строки.
- **Панель строки** (Shift+Enter в режиме ячеек, двойной клик по №, кнопка и пункт меню «Открыть строку»): все поля текущей строки справа, со скрытыми колонками, расчётными полями текстом и ссылками на справочники (`TablePartLinePanel`). Правки сразу идут в строку. Alt+↑/↓ и стрелки в заголовке листают строки.
- **Сканер штрихкодов** (`useBarcodeScan`, `lib/barcode-scan.ts`): часть с «Подбором» принимает сканы с любого места страницы. Сканер отличается от человека по темпу: не меньше 4 символов, не больше 40 мс между нажатиями, в конце Enter. Позиция ищется в справочнике и сопоставляется по `barcode`, `ean`, `gtin`, `code`, `sku`, `article`, `vendorCode`. Найденная прибавляет единицу к своей строке или добавляет новую. Набранное сканером убирается из поля, куда попало, а открытая ячейка закрывается без изменений. Если на странице несколько частей, скан достаётся той, где фокус, иначе первой видимой.
- **Движение строк** (`useRowMotion`): переставленные строки доезжают до нового места примерно за 0,24 с без отскока. Повторная перестановка подхватывает строку с того места, где она видна сейчас. Новые строки въезжают, строки, затронутые подбором, вставкой, заполнением, копированием или сканом, коротко подсвечиваются. При системной настройке «уменьшить движение» всё это мгновенно (общее правило в `globals.css`).

**Подбор** (как «Подбор» в 1С). Команда «Подбор» на панели табличной части, в контекстном меню и по F7 в режиме ячеек открывает `TablePartPickDialog`. Слева справочник с поиском, справа корзина «Подобрано», «Перенести в документ» переносит корзину в часть. Что подбирать, часть узнаёт из метаданных (`pickTarget` в `lib/pick-lines.ts`): позиция — её записываемая ссылочная колонка (сначала обязательная), количество — записываемая числовая колонка с именем вида `quantity`, `qty` или `count`. Без количества подбор добавляет по строке на позицию. Части без ссылочной колонки команды не получают. Отличия от 1С:
- **Корзина рядом со справочником**, а не под ним, и видна во время поиска.
- **Клавиатура не уходит из поиска.** ↑/↓ выбирают позицию, Enter добавляет одну. «3*гвозди» добавляет три из найденного по «гвозди» (количество действует один раз, запрос остаётся). Shift+Enter переводит фокус в количество позиции, а Enter возвращает в поиск. Ctrl/Cmd+Enter переносит корзину.
- **У каждой позиции видно**, сколько её уже в документе и сколько в корзине.
- **Объединение строк.** Позиция, которая уже есть в документе, по умолчанию добавляет количество к своей строке, а не повторяет её (переключатель запоминается в браузере). Типы ячейки при этом сохраняются: строковое десятичное остаётся строкой.
- **Защита от потери подобранного.** Escape сначала очищает поиск. Закрытие с непустой корзиной (Escape, клик мимо окна) не теряет подобранное: окно спрашивает, перенести или закрыть без переноса.
- **После переноса** затронутые строки выделены, в подвале новые итоги, уведомление сообщает, сколько строк добавлено и сколько дополнено.

**Группы.** У иерархического справочника (`Definition.Hierarchy`) слева дерево групп, как в форме подбора 1С. Группы загружаются одним списочным запросом с фильтром `is_folder = true`, дерево собирается на клиенте (`lib/group-tree.ts`). Если групп нет, панели нет. Выбранная группа показывает свои позиции и позиции подгрупп (фильтр `parent_id in_hierarchy`), поиск работает внутри неё, а метка группы у поиска снимает этот фильтр. Сами группы в списке позиций не показываются. С клавиатуры: Shift+Tab из поиска переводит в дерево, ↑/↓ выбирают группу (список меняется сразу), ←/→ сворачивают и разворачивают, Enter возвращает в поиск. Последняя группа запоминается для каждого справочника, и при следующем открытии дерево раскрыто до неё. Без настройки табличная часть работает как раньше: поля ввода в ячейках всегда открыты.

**Frontend Auto-Discovery:**
Платформа генерирует UI для расширений автоматически! Фронтенд получает `/api/v1/meta/entities` и использует generic routes `[routePrefix]` для списка и AutoForm. Запросы/ответы должны быть зарегистрированы в HTTP contracts registry: metadata не разрешает незарегистрированный URL или дополнительное writable поле. Новые сущности автоматически появляются в разделе расширений меню и в палитре команд у пользователей с их правом чтения: `/meta/entities` отдаёт `readPermission` сущности, а `lib/navigation-access` скрывает пункт без него (форма `/new` требует права `create`; пункт с явным `permission` проверяется по нему); custom forms и особое размещение подключаются через frontend registry/navigation. Подробности — [новый справочник](../howto/new-entity.md).

## 3. Точки расширения

Кроме создания новых сущностей, Extension API позволяет "вклиниваться" в стандартные:

1. **Хуки (Hooks):** Инъекция кастомной логики в системные документы.
   ```go
   invoiceService.Hooks().OnBeforeCreate(func(ctx, doc) error { ... })
   ```
2. **Новые Регистры:** Интегратор может написать свой `RegisterVisitor` и `RegisterRecorder`, чтобы документы, реализующие нужные source-интерфейсы начали двигать новые кастомные регистры. Регистры конфигурации подключаются модулем `posting.Module` через `RouterConfig.PostingModules`: модуль добавляет visitors, recorders и проверки в движок и возвращает `MovementProvider` для отчёта о движениях документа. Пример — `cryptoregisters.Registers`.
3. **Атрибуты (JSONB):** У каждой сущности есть поле `attributes` для произвольных данных интегратора. Схемы, валидации, фильтрации и колонок для них нет; типизированное поле добавляется в Go-модель сущности.
4. **CEL Политики:** Написание кастомных правил блокировок (например, запрет проведения документов с суммой > 1 млн) в виде конфигурации через CEL (Common Expression Language), без перекомпиляции Go.

## 4. Модули конфигурации

Конфигурация подключается к платформе модулями, а не правками ядра. В репозитории их две: криптопроцессинг (`internal/configuration/crypto`) и каркас магазина автозапчастей (`internal/configuration/autoparts`, [описание](../autoparts/README.md)). Конфигурации не импортируют друг друга. `make check-configurations` (`scripts/ci/check-configurations.sh`) собирает команды и фронтенд каждой из них и пустой, а `go run ./cmd/http-contracts` генерирует фронтенд-файлы всех конфигураций и проверяет, что платформенные файлы у всех одинаковые.

Конфигурация в целом передаётся платформе значением `configuration.Configuration` (`internal/configuration`):

- `APIVersion()` — версия публичного API (`pkg/sdk`), для которой собрана конфигурация; несовместимую платформа не запустит (`configuration.CheckAPIVersion`);
- `Name()` — имя каталога конфигурации: `db/configuration/<имя>/` и `frontend/configuration/<имя>/`, а также таблицы её истории миграций `goose_db_version_<имя>`. Имя — строчный идентификатор до 40 символов, кроме `platform` и `extensions` (`configuration.ValidName`);
- `Register(reg)` — справочники, документы, регистры, наборы отчётов и их исполнители;
- `RouteContracts()` — HTTP-контракты маршрутов её route modules; контракты сущностей выводятся из реестра;
- `Migrations()` — её миграции тенанта, `nil`, если своих таблиц нет. У них своя история goose и своя нумерация, отдельные от платформенных ([правила](../../db/migrations/README.md#три-истории-версий));
- `IntegrationCatalog()` — каталог интеграций приложения: платформенные назначения и провайдеры вместе с её собственными, в порядке экрана настроек; `nil`, если своих нет;
- `PoolConsumers()` — её справочники, читающие аккаунты через пулы интеграций (`integrations.PoolConsumer`).
- `Server(ctx, env)` — её часть API-сервера (`configuration.Server`): регистрация сущностей с её сервисами времени выполнения, объектные права сессии, модули проведения, route modules и проверки подключений интеграций. Свои настройки она читает сама и возвращает ошибку, если они неверны;
- `Worker(ctx, env)` — её часть воркера (`configuration.Worker`). Для каждого тенанта она возвращает маршруты outbox по типу агрегата (каждый на своём relay; automation-relay их пропускает), долгоживущие компоненты (под супервизором — с перезапуском и метрикой готовности), часовые очистки и проверку схемы;
- `Seed(ctx, env)` — её начальные данные после платформенных (`configuration.SeedEnv`). С `env.Demo` это демо-данные; ID платформенных демо-валют и источников курсов переданы в `env`. Повторный запуск ничего не ломает.

Процессы собирают приложение функциями `configuration.Compose`, `Permissions` и `CatalogDefinitions`, а мигрируют тенанта опциями `configuration.MigrationOptions`. Порядок такой: общие сущности платформы (`internal/platformcontent`), затем конфигурация, затем `extensions.Register`. `platformcontent` — это контрагенты, валюты, организации, договоры, аккаунты и пулы интеграций, источники и регистр курсов. Каталог интеграций и потребителей пулов им передаёт конфигурация. Крипто-конфигурация — `content.Crypto(content.Services{...})`, пустая (только платформа) — `none.New()` из `internal/configuration/none`. Весь Go-код конфигурации лежит под её корнем `internal/configuration/<имя>/` с теми же слоями, что у платформы: `domain/`, `application/`, `infrastructure/`, а точка сборки — `content/`. Крипто-пакет `internal/X` платформенного вида лежит в `internal/configuration/crypto/X`, правила направления зависимостей между слоями действуют и внутри корня. Каждая конфигурация импортирует из платформы только [`pkg/sdk`](../sdk/README.md) и вызывает в своих тестах `sdktest.Check` (обёртку над `configurationtest.Check`). Он проверяет имя, повторяемость регистрации, уникальность прав и маршрутов, генерацию контрактов и файлов фронтенда, наличие платформенных провайдеров в каталоге интеграций и то, что её миграции — это `db/configuration/<имя>/` в формате платформы с версиями ниже `10000`.

Платформенный запуск лежит в `internal/bootstrap/server`, `internal/bootstrap/worker`, `internal/bootstrap/tenant` (команда тенантов) и `internal/bootstrap/seed` (сид). У каждой конфигурации свои тонкие точки входа, которые вызывают их `Main` с ней самой. `cmd/server`, `cmd/worker`, `cmd/tenant` и `cmd/seed` запускают платформу с пустой конфигурацией: без Vault и без отраслевых настроек. `cmd/crypto-server`, `cmd/crypto-worker`, `cmd/crypto-tenant` и `cmd/crypto-seed` запускают крипто, и Docker-образ собирает именно их в `/bin/server`, `/bin/worker`, `/bin/tenant` и `/bin/seed`. Тенант принадлежит одной конфигурации навсегда: её имя записано в meta-базе, и команда тенантов другой конфигурации его не мигрирует. Сервер сравнивает схему тенантов с ожидаемой для своей конфигурации (`configuration.ExpectedSchema`) в мониторе `/admin/tenants`. Интеграционные тесты `internal/bootstrap` проверяют, что сервер с пустой конфигурацией отвечает на `/health/ready` и не монтирует маршрутов конфигурации, а воркер запускает тенанта.

Отдельные точки расширения:

| Точка расширения | Что даёт конфигурация | Пример в Metapus |
|---|---|---|
| `posting.Module` | регистры, visitors/recorders и проверки проведения; возвращает `MovementProvider` | `infrastructure/crypto/cryptoregisters` |
| `v1.RouteModule` (`RouterConfig.RouteModules`) | маршруты на группах из `v1.RouteContext`: `Root`, `API`, `Protected`, `System`, а под своим префиксом — `ProtectedGroup(path)` и `Authenticated(path)` с цепочкой платформы; маршрут, который сам находит тенанта, привязывает его `middleware.BindTenant`; свои зависимости модуль хранит сам | `infrastructure/http/cryptohttp` |
| `auth.WithAccessScopeProvider` | объектные права сессии в claim `scp` | `merchant.NewPortalAccessScopes` |
| `middleware.WithCommandScope` | владелец ключей идемпотентных команд (например, партнёр по API-ключу) | `cryptomiddleware.WithMerchant`, `MerchantPortal` |
| `content.Services` | сервисы конфигурации для регистраций документов вне `v1.DocumentDeps` | ссылки checkout, подписанты согласований |
| `integrations.Catalog` | назначения и провайдеры интеграций конфигурации рядом с платформенными (CoinGecko, Telegram, SMTP). Каталог неизменяем, собирается один раз и передаётся явно: сервисам аккаунтов и пулов, выбору аккаунтов (`integration_repo.NewRuntime`), `RouterConfig.IntegrationCatalog`; HTTP-профили — реестром `profiles.New(...)`. Список провайдеров в БД задаёт миграция конфигурации | `cryptointegrations.Catalog()`, `cryptoprofiles.Registry()` |
| `integrations.PoolConsumer` | справочник, читающий аккаунты через пулы интеграций: пул нельзя удалить или сменить ему провайдера, пока потребитель им пользуется; состав пула и новые ключи аккаунта проверяются по его требованиям. Конфигурация создаёт репозитории аккаунтов и пулов со своими потребителями | `crypto_integration_repo.RPCPoolConsumer` |
| `entity.MovementColumnDef.RefEntity` | колонка-ссылка движения регистра называет сущность, на которую ссылается; по ней разрешаются представление и ссылка `/catalogs|documents/{route}/{id}`. Колонка без `RefEntity` не показывается | колонки регистров `crypto_*` |
| `platform.MovementSourceProvider` | для документа с движениями: какие его поля раскрывают каждую колонку движения. При FLS-политике на документ колонка видна, только если объявлена и все перечисленные поля читаемы; пустой список — колонка-константа | `content/movement_sources.go` |
| `db/configuration/<имя>/` | миграции конфигурации: её таблицы, права и FLS её сущностей, ограничения её правил на таблицах платформы. Они применяются после платформенных `db/migrations/`, у них своя история goose `goose_db_version_<имя>` и своя нумерация (`dbassets.ConfigurationMigrations`) | `db/configuration/crypto/` |
| `spec.Bundle` | контракты HTTP конфигурации; генератор пишет их в её собственные файлы `frontend/configuration/<имя>/{types,lib}/generated/`, а типы платформы импортирует из платформенных файлов (`contracts.GenerateOn`, `contracts.GenerateRoutesOn`) | `configuration.OwnHTTPContractBundles`, `configuration.HTTPArtifacts` |

Граница проверяется тестами в `internal/architecture`:

- `configuration_boundary_test.go`: платформенный пакет не импортирует пакет конфигурации. Пакеты конфигурации — это всё под её корнем (`configurationPackages` — по одной строке на конфигурацию). Список исключений пуст и должен таким остаться;
- `configuration_storage_test.go`: строковые литералы платформенного кода и платформенные миграции не называют таблицы из миграций конфигурации (`db/configuration/*`), а тесты платформы не импортируют конфигурацию; оба списка исключений пусты. Проверки собранного приложения (все HTTP-контракты, актуальность сгенерированных файлов, наборы отчётов конфигурации) лежат в `internal/configuration/crypto/content`, проверки поведения конфигурации — в её пакетах;
- `configuration_commands_test.go`: каждая команда `cmd/` отнесена к платформе или к конфигурации; платформенные команды и их тесты не импортируют конфигурацию и не называют её таблицы. `cmd/http-contracts` отнесён к командам конфигураций: он перечисляет все конфигурации репозитория. Оставшаяся связь `cmd/integration-test`, который готовит общую базу интеграционного прогона с крипто, лежит в замороженном списке; список таблиц конфигурации в командах пуст.

Во фронтенде код конфигурации лежит в `frontend/configuration/<имя>/` (`components`, `lib`, `hooks`, `types`, `stores` с той же структурой, что у платформы), платформенный — в `frontend/components`, `lib`, `hooks`, `stores`, `types`. Страницы и layout конфигурации лежат в `frontend/configuration/<имя>/pages/` по структуре `app/`, вместе с группами маршрутов: `pages/(portal)/layout.tsx` становится `app/(portal)/layout.tsx`.

`frontend/app/` — точка сборки, и её конфигурационная часть генерируется: `npm run configure -- <имя>` (`frontend/scripts/configure.cjs`) собирает `app/` для одной конфигурации, `none` — для платформы без конфигурации.
- Для каждого `page.tsx` и `layout.tsx` из `pages/` генератор пишет в `app/` по тому же пути однострочную обёртку `export { default } from "@/configuration/<имя>/pages/…"`. Next.js маршрутизирует её как обычную страницу и выделяет в отдельный чанк.
- `app/configuration.ts` вызывает функцию регистрации, которую называет манифест конфигурации `frontend/configuration/<имя>/manifest.json` (`{ "register": "registerCryptoConfiguration" }`).
- Сгенерированные файлы не коммитятся. Генератор перечисляет их в `app/.gitignore`, удаляет при сборке другой конфигурации вместе с устаревшими типами маршрутов в `.next` и отказывает, если страница конфигурации заняла бы платформенный файл.
- Имя берётся из аргумента, затем из `METAPUS_CONFIGURATION`, затем из прошлой сборки; по умолчанию `none`. Скрипты `dev`, `build`, `lint`, `typecheck` и тестов сначала запускают генератор с этим выбором.
- На каждую конфигурацию собирается свой образ: аргумент `METAPUS_CONFIGURATION` в `frontend/Dockerfile`, по умолчанию `crypto`. `make frontend` и e2e-тесты Playwright собирают крипто.
- Модульные тесты собранного крипто-приложения подключают его регистрацию сами (`frontend/tests/crypto-configuration.ts`) и не зависят от выбора. `frontend/tests/unit/configure.spec.ts` проверяет генератор.

Тест `frontend/tests/unit/configuration-boundary.spec.ts` проверяет, что:

- платформенные файлы не импортируют `configuration/`, и список исключений пуст;
- платформенный код и маршруты `app/` не используют словарь конфигурации (crypto, merchant, portal, wallet и т. п.), кроме путей модулей;
- `app/` обращается к конфигурации только через такие обёртки и `app/configuration.ts`.

Конфигурация подключает свои части при старте: сгенерированный `frontend/app/configuration.ts` вызывает функцию из её манифеста (у крипто — `registerCryptoConfiguration()`), его импортируют первыми клиентский layout `app/(main)` и страница дашборда.

| Точка расширения фронтенда | Что даёт конфигурация | Пример |
|---|---|---|
| `registerEntityOverlays` (`lib/entity-registry-defaults`) | колонки, видимость, фильтры, форма и список для сущностей из metadata | `configuration/crypto/lib/entity-overlays.ts` |
| `registerWidget` (`lib/widget-registry`) | виджет дашборда со своей схемой настроек (`configSchema`) и редактором (`configEditor`) | `configuration/crypto/lib/widgets.tsx` |
| `registerDefaultDashboard` (`lib/dashboard-layout`) | дашборд пользователя по умолчанию | там же |
| `detailContent`, `renderField` в overlay сущности | панели под формой существующей записи и свои редакторы полей на generic-страницах `[routePrefix]/[id]` | `configuration/crypto/components/detail-panels.tsx` |
| `registerNavigation` (`lib/navigation`) | группы разделов меню (в существующую группу или после указанной), системные ссылки, пункты палитры команд; у пункта может быть `permission` | `configuration/crypto/lib/navigation.ts` |
| `registerRouteEntities`, `registerIcons`, `registerRouteLabels` | ключ сущности, иконка и заголовок вкладки по URL до загрузки metadata | там же |
| `registerWorkspace` (`lib/access`) | отдельный интерфейс для пользователей без доступа к ERP; `landingPath(user)` выбирает его после входа | `configuration/crypto/lib/access.ts` (портал) |
| `createScopedClient(scope)` (`lib/api`) | клиент своей HTTP-области `/<scope>/v1` с общей сессией, проверкой контрактов и идемпотентностью | `configuration/crypto/lib/api/portal.ts` |
| `registerSecurityDimension`, `registerProfilePreset`, `registerAffinityRule`, `registerResourceLabels` (`lib/security-registry`) | RLS-измерение с поиском значений, шаблоны профилей безопасности, подсказки ролей, названия ресурсов прав | `configuration/crypto/lib/security.ts` |
| `registerSettingsPage` (`lib/settings-registry`), `registerAdminSection` (`lib/admin-registry`) | свои страницы в «Настройках» и разделы в «Управлении» | `configuration/crypto/lib/settings.tsx`, `lib/admin.ts` |
| `registerStatusColors`, `registerWorkerJobs` | цвет статусов и фильтры журнала задач воркера | `configuration/crypto/lib/labels.ts` |

Регистрации выполняются при загрузке модуля `app/configuration.ts`, поэтому платформа читает реестры при рендере, а не при загрузке своих модулей. Хранилища конфигурации, сохраняемые в `localStorage`, называются с префиксом `SCOPED_STORAGE_PREFIX` (`metapus-scoped-`): платформа очищает их при смене пользователя, даже если модуль ещё не загружен.

Печатные формы документ конфигурации объявляет через `v1.PrintFormsProvider`; типы областей команд (`command.Metadata.ScopeType`) и маршрутов контрактов — открытые идентификаторы, конфигурация добавляет свои (`merchant`, `portal`) без правок ядра. Состояние раскрытых секций интерфейса хранится в `interface.expandedSections` под ключом, который выбирает UI.

Коды ошибок конфигурации объявляются рядом с её доменом и собираются из `apperror.AppError`; `core/apperror` хранит только платформенные коды. Например, `WALLET_POOL_EXHAUSTED` объявлен в `catalogs/wallet`, `CRYPTO_NETWORK_UNAVAILABLE` в `catalogs/blockchain_network`. Подсказку `details.retryAfterSeconds` любой ошибки `ErrorHandler` выставляет в заголовок `Retry-After`.

## 5. Scaffold CLI

Для ускорения разработки расширений используется встроенный кодогенератор:
```bash
go run cmd/scaffold/main.go --name waybill --type document
```
Генератор создаёт модуль из двух Go-файлов — `model.go` (Definition и модель) и `register.go` (одна строка `v1.Catalog`/`v1.Document`) — и миграцию с актуальными CDC triggers. DTO, репозиторий, сервис и регистрация выводятся из модели (раздел 2). Права модуля миграция не объявляет: `tenant migrate` выводит их из регистрации и выдаёт роли admin. Миграция пишется в `db/extensions/<name>/` с версией 10000+: оттуда она встраивается в бинарники и применяется к тенанту любой конфигурации после платформенных и конфигурационных, с историей `goose_db_version_extensions`. Документ создаётся без табличных частей; `--parts goods,services` добавляет их: `entity.Part` в Definition, поле и тип строки в модели, таблицы `<Table>__<key>` в миграции. `--hierarchical` включает папки и проверки иерархии справочника; без флага справочник плоский.

Общее `entity.Definition` связывает identity, таблицу, маршрут и hierarchy. `contracts/spec.Entity` выводит стандартные HTTP-контракты из Definition и конкретных DTO, `spec.EntityOf` — из типов, построенных во время выполнения (декларативная регистрация). После добавления модуля в `extensions/register.go` выполните `go run ./cmd/http-contracts`; отдельные правки registry/routes для расширения не нужны. Права других ролей, бизнес-поля, локализация, движения и новый worker workflow требуют явной настройки.

Модули `extensions/` компилируются внутри Metapus. Публичный API платформы — `pkg/sdk` ([описание и правила версий](../sdk/README.md)): на нём целиком построена конфигурация «Автозапчасти», а метод `Configuration.APIVersion` проверяется при старте каждой платформенной команды.

## 6. Единый контракт встроенных сущностей и расширений

Все встроенные справочники и документы предоставляют domain `Definition`. Модель реализует `EntityDefinition()`; generic `EntityRegistration[Model]` выводит identity и metadata, `CatalogRegistrationFor[Model,Create,Update,Read]` также выводит стандартные transport contracts. Нулевое значение регистрации работоспособно: передавать Definition вручную в struct literal не требуется.

Factory contracts требуют Definition и HTTP bundle. Стандартные DTO и маршруты codegen получает из того же registry, что и сервер. Разрешённые document capabilities ограничивают набор сгенерированных маршрутов; custom команды и специальные detail projections объявляются у владельца документа.

Catalog service и repository читают hierarchy из Definition, включая type, folder restrictions и max depth. Глобальный реестр hierarchy удалён; прямые repository writes используют ту же политику, что и service. Для отдельного тестового ограничения передайте копию Definition с нужной Hierarchy.

## Extension API 2.0

Добавлены обязательные Definition и HTTPContracts у factory registrations. CatalogServiceConfig принимает Definition вместо строкового EntityName; глобальные GetCatalogMeta/RegisterCatalogMeta удалены. Внешний модуль на прежнем API должен перейти на EntityDefinition, typed registration и Definition-based repository/service constructors. Новые scaffold-модули сразу используют API 2.0.
