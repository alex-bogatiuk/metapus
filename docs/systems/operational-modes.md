# Операционные режимы (Operational Modes)

> **TL;DR:** Metapus всегда использует физическую изоляцию `Database-per-Tenant`. Все экземпляры server и worker в одном развёртывании запускаются из одного релиза и работают с одной ожидаемой версией схемы.

> **Тип:** Concept
> **Аудитория:** DevOps, Architect
> **Связанные:** [multi-tenancy.md](multi-tenancy.md)

---

## 1. Общие принципы

В бизнес-коде (Domain/HTTP/Repo) не пишутся SQL-запросы с `WHERE tenant_id = ?`. Middleware выбирает пул соединений к физически отдельной базе tenant-а и передаёт его через `context.Context`.

Shared DB для данных разных клиентов не поддерживается. Версия приложения также не назначается отдельным tenant-ам: по-тенантные rollout, маршрутизация между версиями и обновление из UI отсутствуют.

Обновление выполняется внешним оператором или CI/CD-процессом:

1. Собрать и проверить единый релиз server, worker, tenant CLI и frontend.
2. Сделать резервные копии meta- и tenant-БД.
3. Остановить server и worker, чтобы исключить обращения к меняющейся схеме.
4. Выполнить `tenant init-meta`, затем `tenant migrate --all` бинарником нового релиза.
5. Запустить server, worker и frontend из того же релиза и проверить readiness.

CLI завершает работу с ненулевым кодом, если миграция хотя бы одной tenant-БД или запись её `schema_version` завершилась ошибкой. В таком случае сервисы остаются остановленными до ручного устранения причины или восстановления из резервной копии.

## 2. Cloud SaaS

Несколько экземпляров server и worker можно масштабировать горизонтально, но все они должны использовать один release artifact. Активные tenant-ы обслуживаются без фильтрации по версии приложения. Миграции выполняются централизованно во время согласованного maintenance/drain window.

## 3. Self-Hosted Multi-Tenant

Все базы дочерних компаний работают с одной версией приложения. Обновление выполняется синхронно для meta-БД и всех активных или приостановленных tenant-БД командой `tenant migrate --all`.

## 4. Dedicated Single-Tenant

В meta-БД создаётся одна запись tenant-а, а frontend или прокси передаёт его `X-Tenant-ID`. Процедура обновления остаётся той же: внешнее развёртывание нового релиза и ручной запуск миграций без служебного агента и доступа к Docker Socket.
