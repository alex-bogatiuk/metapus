# Автонумерация (Numerator)

> **TL;DR:** Сервис автогенерации кодов для справочников и номеров для документов. Поддерживает настройку префиксов, включение года и два режима производительности (Strict и Cached).

> **Тип:** Concept
> **Аудитория:** Developer
> **Связанные:** [crud-pipeline.md](crud-pipeline.md)

---

## 1. Конфигурация нумератора

Формат номеров задаётся объектом `Config`:
- `Key`: стабильный ключ счётчика, например `catalog.organization`. Если он задан, смена `Prefix` продолжает ту же последовательность. Без него счётчик определяется префиксом.
- `Prefix`: "INV", "GR", "CP" (Счет, Поступление, Контрагент).
- `IncludeYear`: `true` добавит год, например `INV-2024-00001`.
- `PadWidth`: ширина числовой части с ведущими нулями (5 -> `00001`).
- `ResetPeriod`: как часто сбрасывать счётчик ("year", "month", "never").

## 2. Стратегии выдачи (Strategies)

### Strict Strategy (Строгая)
Выделяет следующий номер непосредственно в БД без предварительного резервирования диапазона. Откат счётчика вместе с документом возможен, когда оба работают в одной транзакции; самостоятельная выдача номера не гарантирует отсутствие пропусков.
- Делает SQL `UPDATE sys_sequences` для **каждого** номера.
- Оптимально для строгой бухгалтерской отчётности (например, Счета-фактуры).

### Cached Strategy (Кешированная)
Гарантирует **максимальную производительность**.
- Делает SQL запрос для резервирования блока (например, 50 номеров) за раз, а затем раздаёт их из памяти (per-key mutex).
- **Минус:** при перезапуске сервера неиспользованные номера из зарезервированного блока "сгорают" (образуются пропуски).
- Оптимально для массового импорта или внутренних технических документов.

## 3. Коды справочников

Правило кода объявляет `entity.Definition.Code` (`internal/core/entity/code_rule.go`), а исполняет `domain.CatalogService` при создании и изменении элемента — для стандартного `v1.Catalog`, для справочника с собственным `.Service(...)` и для явной регистрации одинаково.

| `CodeRule.Source` | Пустой код при записи |
|---|---|
| `CodeFromSeries` (по умолчанию) | Платформа берёт следующий код серии справочника, например `ORG-000001` |
| `CodeDerived` | Код выводят хуки справочника (валюта — из ISO-кода, токен — из тикера). Если он остался пустым, запись отклоняется |
| `CodeManual` | Запись отклоняется: код вводит пользователь |

Серия справочника непериодическая. Счётчик определяется ключом `catalog.<key>`, а `Prefix` (по умолчанию — из ключа сущности) и `Width` (по умолчанию 6) задают только формат:

```go
var Definition = entity.Definition{
	Key: "organization", Name: "Organization", Route: "organizations", Table: "cat_organizations",
	Kind: entity.CatalogKind,
	Code: entity.CodeRule{Prefix: "ORG"},
}
```

Код присваивается последним шагом перед `repo.Create`/`repo.Update`, после хуков `Before*` и проверок, в той же транзакции. Ошибка записи откатывает и счётчик. Введённый пользователем код сохраняется; код серии, который уже занят другим элементом, пропускается. Повтор занятого кода возвращает `409` с `field: "code"`.

Присвоенный код не меняется сам: изменение без кода (например, `PUT` без поля `code`) сохраняет код, который уже записан. Новый код серии получает только элемент, у которого кода нет и в базе.

**Элементы без кода из прошлых версий.** `migration.RunAll` с `WithCatalogCodes(content.CatalogDefinitions(...))` (так его вызывают `cmd/tenant` и `cmd/integration-test`) после миграций нумерует непомеченные на удаление элементы с пустым кодом в справочниках с серией. Порядок — по `id`, счётчик тот же, что у `CatalogService`, занятые коды пропускаются, `version` увеличивается. Повторный запуск ничего не меняет.

## 4. Номера документов

`BaseHeaderDocumentService.GenerateNumber` и `BaseDocumentService.GenerateNumber` присваивают пустой номер при создании и проведении по `NumeratorPrefix` сервиса (формат `PREFIX-YEAR-00001`, годовая серия). **Transaction-aware:** `getQuerier` сначала использует переданный через context TxManager, реализующий querier; при его отсутствии использует tenant Pool. Поэтому выдача номера участвует в транзакции записи.

## 5. Tenant-Aware (Мультитенантность)

Поскольку `Cached Strategy` хранит пулы номеров в оперативной памяти (RAM) сервера, ключи кеширования включают `TenantID` (например: `5cfe45cb...:INV_2024`). Это предотвращает случайную выдачу номера тенанта А документу тенанта Б.
