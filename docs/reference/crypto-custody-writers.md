## 1. Общий механизм

[CryptoBalanceVisitor](../../internal/domain/posting/crypto_visitor.go) собирает движения документов. CryptoBalanceRecorder → [crypto_balance.Service](../../internal/domain/registers/crypto_balance/service.go) → [CryptoBalanceRepo](../../internal/infrastructure/storage/postgres/register_repo/crypto_balance.go) → [BaseAccumulationRepo](../../internal/infrastructure/storage/postgres/register_repo/base.go) записывают reg_crypto_balance_movements.

Generic reversal использует appendReversalsByRecorder с source line и остатком компенсации. Это новый факт отмены, а не новое поступление из сети.

Immutable movements и SQL-trigger balances сохраняют физическую историю. Идемпотентность recorder/line ID защищает конкретный канал записи, но сама не исключает проведение того же chain effect другим recorder.

## 4. Порядок блокировок и границы перехода

- Generic posting имеет document advisory lock и сортированные financial resource keys; фактические scope locks добавляют validators/SQL guards.
- Operating receipt берёт AML scope до записи financial/resource facts.
- Fee budget использует owner/scope locks до reservation/payer balance.
- Provider reconciliation/opening использует account → operation → incident.
- Схема 80 согласует участвующий inbound: document advisory lock, если payment уже известен → AML scope → catalog wallet → payment row → wallet/token balance → logical effect → strict proof/catalog guard. Несколько scope/wallet keys берутся в стабильном порядке. LockIncomingEvent выполняет ранний захват до matching; FinancialReorgRepo использует тот же порядок для payment.
- SaveVerification сначала берёт recipient AML scopes, затем выполняет ObserveVerification и индексирует proof. Accounting index берёт wallet/token balance до logical effect; он не захватывает catalog wallet после balance. Orphan proof блокирует известные aliases без создания новой occurrence.
- Receipt intake и funding используют общий LockIncoming: scope → catalog wallet → balance → logical effect. Maintenance policy FOR SHARE для receipt берётся после этих locks. Общий BEFORE INSERT guard старых writers берёт ту же balance row, включая отсутствие проекции; ожидавший writer после коммита видит новый claim/запрет. Funding допускает только platform-owned external receipt.

В financial recognition registry подключены CryptoCustodyReceipt, CryptoWalletFunding, final CryptoNativeFunding, sweep model 2, treasury model 2, merchant withdrawal model 2 и custody loss model 2. CryptoPayment custody не владеет: он распределяет receipt своего перевода (§8). Схема 86 добавляет отдельный fee effect/proof/binding для новых fee reservations model 2; legacy model 1 не принимается автоматически. Исторические движения не принимаются автоматически. Migration 77 создаёт только индекс проверенных identity/occurrence/evidence. Наличие строки в нём не означает приём денег, актуальную canonicality, merchant ownership или разрешение подписи.

P3 должен согласовать порядок locks остальных outbound/settlement writers до их включения в registry. Проверки схемы 80 доказывают, что ожидающий AML scope proof/incoming path не удерживает wallet/balance/effect; это не завершение перехода всех writers. JIT порядок схемы 81 приведён в §9, sweep схемы 82 — в §10.

## 5. Проверяемый identity foundation

Реализовано:

- AccountingTransferBasis и независимый CustodyEffectGuard; strict path не наследует legacy bypass неактивированного ingestion. Wallet funding CLI использует общий transfer basis без фиктивного payment.
- Независимый accounting-effect.v1 с transaction-local ordinal EVM и полным trace/call-value identity TRON.
- Optional accountingIdentity в новых TransferVerification; прежние decoder/economics/signing схемы сохраняются.
- Неизменяемые logical effects, block occurrences и связи к persisted proof; SQL/Go golden key совпадает.
- Конкурентный replay, новый block occurrence без второго logical effect, conflict payload/alias, ограничения прямого SQL.
- Legacy proof без identity не получает выдуманный ordinal при replay; для его admission потребуется проверяемый backfill.

## 6. Receipt и невыясненные

[ReceiptIntakeService](../../internal/application/cryptoapp/receipt_intake_service.go) и [ReceiptIntakeRepo](../../internal/infrastructure/storage/postgres/crypto_repo/receipt_intake.go) атомарно создают документ, physical receipt, равный ему suspense, posting ownership, recognition, audit и один `posted` outbox. Повтор occurrence или другая occurrence того же logical effect (re-inclusion) возвращает прежний receipt; изменение wallet/token/amount/reason даёт conflict. Документ нельзя редактировать, перепроводить или распроводить.

Кто создаёт receipt:

- worker `runReceiptIntakeLoop` — финальный несопоставленный перевод поддерживаемого актива на управляемый кошелёк (причины `no_allocation`, `wrong_token`, `dust` и т. д.; без счёта — через 30 минут ожидания позднего сопоставления);
- обработчик событий в момент финальности сопоставленного перевода — причина `matched_receipt`, в той же транзакции платёж распределяет receipt (§8).

Аудит каноничности (`reg_crypto_custody_receipt_audits`, worker `runReceiptAuditLoop`, каждые 15 минут) — единственная проверка отсутствия учтённого перевода; отдельного аудита платежей нет. Доказанное отсутствие в одной транзакции:

1. сторнирует распределение каждого проведённого платежа этого receipt через обработчик событий (`FinancialReorgRepo`, hold `posted_payment_reorg`);
2. помечает receipt `orphaned`, открывает инцидент `deep_reorg`, ставит hold на сеть и кошелёк.

Если платёж сторнировать нельзя, откатывается всё, и аудит повторяет попытку. После orphan receipt нельзя распределить (SQL-guard). Перевод, повторно включённый в другой блок, переякоривает аудит на доказательство нового блока (`anchor_verification_id`): иначе аудит сообщил бы об отсутствии в старом блоке. Якорь может указывать только на каноническое доказательство той же транзакции.

Ручное зачисление ([MerchantCreditService](../../internal/application/cryptoapp/merchant_credit_service.go), документ `CryptoMerchantCredit`) списывает весь остаток невыясненных по тарифу мерчанта на момент подготовки. Оно запрещено для receipt в состоянии orphan и для receipt, чей платёж не проведён после reorg (состояние журнала `payment_reorged`): при повторном включении перевода платёж распределит его снова. Оба запрета продублированы в `fn_crypto_merchant_credit_guard`.

Receipt не начисляет merchant net, processing fee, provider balance или platform cost. Невыясненные привязаны к receipt, а не к кошельку, поэтому свип и вывод их не расходуют (P5).

Карточка receipt — `GET /crypto/unidentified-receipts/:id`: доказательство (текущий якорь аудита, источники), состояние аудита, остаток и документы распределения с суммой, которую каждый удерживает после сторно.

## 7. Funding CLI схемы 79

TRON сохраняет полный независимый verification proof; EVM теперь делает то же через read-only TransferVerifier без signer, Vault deriver и nonce manager. Единственный RPC не разрешает funding. Native EVM funding требует доказанного отсутствия executable recipient code (`matchingEffects=1`); неизвестная native coverage не разрешает приход. Общий strict guard действует независимо от ingestion activation и сохраняет исторические evidence bytes.

Funding допускает внешний sender и platform-owned recipient. Managed sender либо expected internal transfer передаётся существующему settlement owner. Merchant-owned funding требует AML operating receipt; CLI не подменяет этот workflow. Ledger semantics существующего operator funding сохранены: suspense, merchant credit, fee, provider balance и доход от неизвестного прихода не добавляются.

Один коммит включает funding receipt, shared posting/recognition, точный physical receipt, неизменяемый audit и `recorded` outbox. Повтор occurrence возвращает прежний receipt; разные effects одной tx не блокируют друг друга. Re-inclusion уже признанного effect и старые funding rows без registry требуют explicit investigation/adoption. Migration не переписывает proof, не создаёт новый principal и не выполняет backfill по разнице balances.

SQL защищает от funding/payment пересечения в обоих порядках, в том числе если legacy payment уже ждёт balance lock. При наличии indexed payment proof сравнивается logical identity; без него совпадение transaction/kind/destination/asset считается неоднозначным. Неполный funding set, движение без recognized receipt и attributed movements с funding recorder запрещены. Использованная схема 79 требует forward migration.

Некомпенсированная положительная ручная custody correction без recognition требует explicit adoption: она могла уже включить этот перевод в остаток. Funding также требует равенства balance projection сумме физических movements и не исправляет расхождение дополнительным приходом. Полностью компенсированная correction сама по себе admission не блокирует.

Проверки: конкурентный replay, разные effects одной tx, funding/receipt race, payment-before-funding и funding-before-payment, ожидающий payment INSERT, managed sender/merchant owner, orphan/re-inclusion, outbox fault injection, manual correction/projection mismatch, сохранение истории при 78 → 79 и полный EVM путь через два локальных RPC-источника.

## 8. CryptoPayment как распределение receipt

В момент финальности сопоставленного перевода обработчик событий учитывает receipt перевода (`RecordPaymentReceipt`, причина `matched_receipt`), а платёж в том же коммите получает `receipt_id` и проводит движения распределения: невыясненные −gross, мерчант +net, комиссия +fee по снимку тарифа. Движений по кошельку у платежа нет (SQL-guard «never moves custody»). Полноту набора на коммите проверяет отложенный инвариант `fn_crypto_assert_payment_attribution`; превышение остатка receipt отклоняет `CHECK(amount>=0)` баланса невыясненных. Снимок тарифа и gross после проведения заморожены (`trg_crypto_payment_frozen_basis`).

Reorg проведённого платежа:

- доказательство отсутствия — независимое (`AuthorizeReorg`); источник — наблюдение watcher (chain observation) или аудит receipt (§6);
- `FinancialReorgRepo` сторнирует merchant, fee и списание невыясненных этого posting generation (сумма возвращается на receipt), открывает инцидент `posted_payment_reorg` и hold сети;
- платёж переходит в `reorged`, распроводится, но сохраняет `receipt_id`.

Повторное включение того же перевода реактивирует тот же платёж, находит исходный receipt по логическому эффекту, переякоривает его аудит и проводит следующее posting generation. Предыдущее поколение должно быть полностью сторнировано.

Ручная корректировка `payment_reversal` возвращает распределение в невыясненные (регистры suspense/merchant/fee, основание `payment_attribution`); платёж остаётся проведённым, поэтому такой остаток можно зачислить вручную.

Удалены: `PaymentRecognitionService`, `reg_crypto_payment_custody_bindings`, поколения custody-признания платежа, явный adoption и отдельный аудит каноничности платежей (`runCanonicalityAuditLoop`, столбцы `*_canonicality_*` у `doc_crypto_payments`).

Проверки: [payment_attribution_integration_test.go](../../internal/infrastructure/storage/postgres/crypto_repo/payment_attribution_integration_test.go), [receipt_reorg_attribution_integration_test.go](../../internal/infrastructure/storage/postgres/crypto_repo/receipt_reorg_attribution_integration_test.go) и сквозной [payment_reorg_e2e_integration_test.go](../../internal/infrastructure/crypto_worker/payment_reorg_e2e_integration_test.go): watcher → платёж → receipt и зачисление → reorg → сторно → повторное включение; orphan от аудита receipt сторнирует платёж в одной транзакции.

## 9. JIT native funding схемы 81

[NativeFundingEvidenceService](../../internal/application/outboundapp/native_funding_evidence.go) получает ожидаемый native transfer из immutable funding intent и controlled catalog addresses, проверяет его независимым TRON/EVM verifier и сохраняет indexed proof до финансовой транзакции. Финальность transaction receipt не заменяет доказательства principal. Отсутствие verifier/quorum, неизвестная accounting identity, другая сумма/сторона/occurrence или orphan оставляют settlement повторяемым без денег. TRON legacy ingestion mode сам по себе не отменяет требование независимого proof.

[NativeFundingSettlementService](../../internal/application/cryptoapp/native_funding_settlement_service.go) использует общий registry для обеих controlled сторон. В одном коммите обязательны один posting generation 1, две точные recognition/physical lines одинакового principal, immutable binding, один `CryptoNativeFunding.custody_recognized` outbox, нормализованный final settlement и точные fee/cost facts. Суммарный principal между managed wallets равен нулю; расходуется только network fee. Источник и получатель должны иметь одну сеть и одного immutable custody owner. Merchant net/processing fee/provider balance не создаются.

Порядок блокировок с 89: полный набор owner/network scopes для source/destination/payer → catalog wallets по ID → funding row → fee reservation → оба wallet/token balances по ID → logical effect. Source/destination owner проверяется до locks; ошибочный межвладельческий перевод не добавляет второй scope после wallet. Обе стороны берутся до effect, и reservation берётся до balance, как в FeeBudgetManager.

Recovery проверяет strict evidence независимо от paused ingestion, network kill switch, parent expiry и текущего signing/AML readiness. Новые external admission пути сохраняют свои запреты. Поздний High не стирает завершённый chain факт и следует за operating capital. Reverted tx не создаёт principal; комиссия учитывается по прежнему ChainReceipt workflow. Cap violation сохраняет hold без principal. Principal proof не расширяет полноту fee evidence: отдельные independent fee proof и accounting identity/role ещё требуют следующего этапа.

Intent, сеть, asset, owner wallets, сумма, attempt и уже закреплённые tx/reservation неизменяемы. `Create` replay сравнивает сохранённые economics. SQL требует создания обеих новых principal lines в текущей транзакции и запрещает неполный набор, раннее освобождение principal через отдельный successful fee settlement (также при fee=0), новую merchant attribution, generic reversal и новое native generation. Indexed native tx требует strict payment recognition также при старом observation alias; одинаковый tx hash не даёт обхода через unindexed payment. Новая occurrence/reorg требует отдельного recovery workflow, которого пока нет. Финансовое использование схемы 81 запрещает Down.

Исторические settled funding rows и их financial/proof bytes не меняются и не принимаются в registry автоматически. Незавершённые fundings после обновления требуют свежего indexed proof перед principal. Sweep model 2 подключён следующим этапом, схема 82 (§10); прежний агрегированный broadcast остаётся только у model 1.

Проверки: concurrent settlement/leases, recovery после parent expiry и kill switch, обе стороны + один outbox, rollback отсутствующего proof/claim/receipt/outbox, orphan, неизменяемый basis и запрет payment alias/reversal, reverted/provisional/cap outcomes; AML operating capital, late High, paused ingestion и совпадение final settlement block.

## 10. Финальный sweep схемы 82

[SweepEvidenceService](../../internal/application/outboundapp/sweep_evidence.go) читает подписанный transfer basis и получает независимый indexed proof до финансовой транзакции. `VerifyExpectedTransfer` TRON/EVM ищет effect по signed economics, не предполагая заранее observation index; два одинаковых подходящих эффекта отклоняются. EVM возвращает фактический global index и transaction-local accounting ordinal. Старый `VerifyTransfer` сохраняет строгую проверку заданного index и прежние evidence bytes. Native proof дополнительно требует единственное покрытое matching effect.

## 15. Маршрутизация ожидаемых переводов схемы 87

Lease, claimant, hold/error, transaction identity, financial amounts и подпись не меняются. Уже завершённая операция подтверждает доставку без повторного открытия. Producer не берёт financial balance/effect/business-document locks и создаёт только immutable request/route facts. Delivery projection отделена от request: worker не удерживает queue lock перед ожиданием financial resources. Owner update и delivery attempt коммитятся вместе; duplicate delivery безопасен, внешних I/O в транзакции нет. За фактическое получение RPC proof и финансовый набор отвечает прежний settlement service.

SQL BEFORE guards запрещают external CryptoPayment creation/receipt и shared posting с expected principal под чужим recorder. Original settlement recorder разрешён только через исходное basis/document relation. Уже занятая logical route и противоречащий registry owner требуют расследования. Fee role схемы 86 отделена; ни fee proof, ни handoff не подтверждают principal. На этапе 87 generic manual corrections без chain basis и другие непереведённые legacy writers оставались P3/P12; новые source-bound corrections добавлены схемой 88 (§16), historical adoption остаётся P12. Общий cutover не объявлен завершённым.

Проверены concurrent replay, полный economic mismatch, canonical hash/address aliases, delayed proof, expired/failed signing label, ambiguous intent/coverage, historical proof/envelope без выдуманной identity, re-inclusion без новых денег, direct SQL ownership/outbox guards, upgrade 86→87 без изменения match history, защищённый Down. Для funding оба порядка watcher/settlement дают одинаковый principal/fee результат. Handoff funding/sweep/treasury/withdrawal сохраняет действующий lease и не создаёт денег.

Операционная проверка pending handoff:

```sql
SELECT r.expected_effect_id,r.owner_type,r.owner_id,
       route.effect_id IS NOT NULL AS has_verified_route,
       d.delivered_at,d.next_attempt_at,d.attempts
FROM reg_crypto_expected_transfer_requests r
LEFT JOIN reg_crypto_expected_transfer_routes route USING(expected_effect_id)
LEFT JOIN sys_crypto_expected_transfer_deliveries d USING(expected_effect_id)
WHERE route.effect_id IS NULL OR d.delivered_at IS NULL
ORDER BY r.requested_at;
```

`delivered_at` означает передачу исходному poller, а не завершённый financial settlement. Не следует удалять request/route или снимать signing/financial holds ради пустой очереди. История не backfill-ится автоматически; после первого request/route Down закрыт.


## 16. Основание ручных корректировок

[FinancialAdjustmentRepo](../../internal/infrastructure/storage/postgres/crypto_repo/financial_adjustment.go) различает два основания:

- `payment_attribution` (режим `payment_reversal`) — сторно распределения текущего settled/posted поколения платежа: выбранные строки merchant и fee получают противоположные движения, а сумма возвращается в невыясненные receipt. Custody не меняется, платёж остаётся проведённым, остаток можно зачислить вручную (§6).
- `wallet_variance` (режим `wallet_balance`) — расхождение кошелька: одна custody-строка и соответствующая строка variance. Основание никогда не берётся из evidence, tx hash или verification ID и не доказывает отсутствие дубля.

Выбор строк фиксируется в транзакции предложения; утверждение заново проверяет поколение платежа. Порядок блокировок: advisory lock документа-основания → custody scope → кошелёк → платёж → корректировка. Maker/checker и step-up обязательны; повтор сверяет payload и автора.

Отложенные SQL-guards требуют ровно выбранные противоположные движения с теми же измерениями и суммами. Generic CryptoAdjustment не может стать владельцем эффекта в общем реестре признания и не создаёт нового входящего principal. Пропущенный приход исправляется через receipt, а не корректировкой.

## 17. Порядок ресурсов учёта схемы 89

Maintenance receipt/adoption берёт scopes → maintenance policy → wallet, как fee reserve берёт scopes → policy → payer. Повторный maintenance guard сохраняет проверку перед проведением. Treasury final settlement берёт wallet до revenue balances; treasury principal reservation берёт wallet до document row/balance/FK и повторно проверяет исходную identity. ## 18. Selectors и activation схемы 90

[00090](../../db/migrations/00077_crypto_custody_accounting.sql) добавляет два lock-only helper:

- `fn_crypto_try_lock_custody_wallets(wallets, scope_merchant DEFAULT NULL, scope_network DEFAULT NULL)` берёт сортированное объединение всех wallet-owner scopes и, если передано, scope заявки, затем уникальные wallets по ID. `NOWAIT` позволяет пропустить занятый набор. Exception subtransaction освобождает весь частично полученный набор при `lock_not_available`, сохраняя внешнюю транзакцию. Пустой/некорректный набор и отсутствующий wallet вызывают constraint error.
- `fn_crypto_lock_withdrawal_wallets(wallets, scope_merchant, scope_network)` блокирует то же объединение scopes, затем wallets. Scope заявки обязателен, даже если legacy principal/fee/funding wallets принадлежат другому владельцу. Пустой wallet set допустим для отмены до появления ресурсов.

Legacy withdrawal сначала получает request advisory и advisory связанного execution, затем полный набор ресурсов, затем request row. В набор входят principal reservations, fee payers, execution source и незавершённые native-funding стороны. Новый selector читает ranking без balance locks и пробует кандидатов последовательно; replay валидирует сохранённый резерв и получает его ресурсы блокирующим способом. Перед записью повторно проверяются request identity и текущая liquidity. Failure/signing publication и broadcast completion используют тот же prefix. AML completion получает source-line/fee/funding wallets до line row. Дебет мерчанта, суммы резервов и правила available balance не меняются.

Legacy sweep claim выполняет короткую транзакцию: планирует source + выбранные collectors, пробует полный набор и затем отдельным statement повторяет eligibility/amount checks на свежем snapshot. `MATERIALIZED` ограждает planning от переноса lock predicate до группировки. Второй statement ограничен уже выбранными sources и заблокированными collectors: новый collector не может добавиться поздним FK. Занятый collector оставляет свой source доступным другим транзакциям; независимый набор может быть выбран в том же batch. Draft linking получает отсортированные attempt advisories и document advisory, затем union существующих и предлагаемых wallets до attempt rows и FK.

Activation coordinator получает workflow advisory → advisory существующего `CryptoNetworkOperation` → полный набор payer/target scopes и wallets → activation row. Проверяются network/target/basis, fee reservation и linked identity после row lock. Broadcast без связанного operation использует source из task; finalization требует существующий operation. Reverted activation заранее владеет target wallet, а фактический fee остаётся у единственного network-operation owner.

PostgreSQL wait-edge tests проверяют withdrawal wallet до request row, activation target до workflow row и operation advisory до payer/target. Полные `crypto_repo`, `funding` и worker integration suites, Go race suite, build, production/integration lint, 436 HTTP contracts, TypeScript и ESLint прошли. Тесты работали на временном PostgreSQL; рабочая БД не обновлялась.

Миграция меняет только сериализацию, не добавляет финансовых фактов и не переписывает историю. Down удаляет два helper; старый runtime нужен до их удаления. ## 21. Queue barriers и semantic replay — этап 93

Схема остаётся 91. Изменены application/repository проверки; миграция и переписывание исторических evidence/движений не требуются.

`CaptureNextAMLInventoryAllocation` получает scope через `FOR UPDATE SKIP LOCKED` до queue row, inventory/resource positions и capture/ack. Producer hooks берут тот же scope до enqueue, поэтому финальная финансовая запись, ожидающая capture, после его commit заново поставит работу в очередь. Отсутствие ready evidence допускает ack старой записи; ошибка проекции откатывает компоненты в savepoint и сохраняет bounded retry. Эти механизмы выбора, применения и обработки ошибок сохранены.

Barrier требует нового statement snapshot после scope lock. Собственная транзакция capture использует `read committed`; при внешней транзакции метод теперь проверяет фактический `transaction_isolation` и отклоняет иной уровень до выбора/ack. В repeatable-read/serializable старый snapshot не становится свежим после ожидания scope и может не видеть уже завершившегося последнего producer. Это изменение контракта вложенного вызова: такой capture нужно вынести в отдельную read-committed транзакцию, а не продолжать с устаревшим snapshot. Production maintenance cycle уже вызывает capture отдельно.

[SigningAuthorizationService](../../internal/application/outboundapp/signing_authorization.go) сравнивает существующий tuple с запрошенной authorization в обоих путях: предварительный lookup и чтение после `ErrSigningAuthorizationExists`. Сравниваются все поля связанного authorization body: schema/tenant/merchant, basis/purpose/attempt/generation, network/profile, addresses/key, asset standard/contract/amount, max fee, fingerprint/sequence, policy и approval digest. Дополнительно проверяются source wallet ID, envelope schema/family/generation/sequence и fingerprint, заново вычисленный из сохранённого canonical unsigned payload. Свежий generated authorization ID и новая calculated expiry исключаются из сравнения; возвращаются исходные ID/deadline/JWS/bytes. Повтор не продлевает authority, а истёкший unsigned authorization не получает новый dispatch. Конфликт останавливается до control signer и permit.

[Fee settlement replay](../../internal/infrastructure/storage/postgres/outbound_repo/fee_settlement_replay.go) теперь проверяет и model 1, и model 2: точный normalized owner, status, block/hash/height, native asset, actual fee и reservation binding; normalized component names/amounts/quantities должны составлять тот же полный набор. Непустой breakdown требует уникальных непустых names, неотрицательных quantities и суммы, равной total fee; legacy report без breakdown остаётся допустимым. Raw RPC evidence, observation time и рост финальности/confirmations не меняют первую запись учёта; сравниваются устойчивые economics. Model 2 по-прежнему дополнительно требует independent fee proof и собственный binding.

Хеши в hints сравниваются без учёта регистра hex, первый записанный текст сохраняется.
