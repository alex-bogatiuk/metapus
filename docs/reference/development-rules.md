# Правила разработки

> **TL;DR:** Строгие инварианты при написании кода. Нарушение этих правил классифицируется как архитектурная или логическая ошибка.

> **Тип:** Reference
> **Аудитория:** Developer
> **Связанные:** [02-architecture.md](../guide/02-architecture.md)

---

## 1. Архитектура и слои

- **Core не импортирует внешние слои проекта**. Допустимы используемые им фундаментальные библиотеки, например UUID, decimal и CEL; это не правило «только stdlib».
- **Domain не импортирует Infrastructure/HTTP**. Никаких импортов `github.com/gin-gonic/gin` или `github.com/jackc/pgx/v5` в слое бизнес-логики.
- **Нет `any`/`interface{}`** в бизнес-логике. Если нужен обобщённый тип — используйте Go Generics (`[T any]`).
- **Handler — это тонкий адаптер**. Запрещено писать `if` с бизнес-условиями в HTTP-хэндлерах.

## 2. База данных и транзакции

> [!IMPORTANT]
> База данных является единой точкой синхронизации.

- **Database-per-Tenant**. Запрещено добавлять `tenant_id` в бизнес-таблицы (документы, справочники).
- **Финансовые crypto movements — append-only**: UPDATE/DELETE запрещены, отмена добавляет противоположные движения через `AppendReversalsByRecorder`. Legacy settlement register имеет отдельную реализацию reversal; не переносите его DELETE-контракт на crypto ledger.
- **Никаких ORM**. Только сырой SQL (`pgx`) и query builder (`squirrel`).
- **Сортировка ресурсов (Resource Ordering)**. При использовании `SELECT FOR UPDATE` для массовых обновлений (например, списании остатков) ресурсы **обязаны** быть предварительно отсортированы по ID для предотвращения deadlock-ов (AB-BA).

## 3. Обработка ошибок

- **Единая точка выхода**. Все ошибки всплывают наверх. В хэндлере: `c.Error(err) + c.Abort()`.
- Запрещено использовать `c.JSON(status, error)` в хэндлерах напрямую. Этим занимается `ErrorHandler` middleware.
- **Оборачивание (Wrapping)**. Все ошибки должны оборачиваться для трейсинга: `fmt.Errorf("action description: %w", err)`.
- Использовать только ошибки `apperror.AppError` с явными кодами.

## 4. Многопоточность (Concurrency)

- **Контекст обязателен**. Каждая запущенная `go func()` должна принимать `context.Context` и слушать `<-ctx.Done()`. Запуск горутин без остановки — утечка памяти (Goroutine leak).
- В worker pool использовать семафоры и `sync.WaitGroup` для Graceful Shutdown.
- Запрещено писать в ResponseWriter (SSE/JSON) из нескольких горутин одновременно. Сбор данных идёт в канал, а пишет одна главная горутина.

## 5. Валидация и вычисления

- Метод `Validate(ctx)` структуры не имеет права ходить в БД или сеть. Только чистые проверки в памяти (числа > 0, строки не пустые).
- Метод `GenerateMovements()` для документов должен быть абсолютно **детерминированным** (один и тот же вход всегда даёт один и тот же выход без сайд-эффектов).

## 6. Миграции (Ранний этап)

> [!WARNING]
> Пока платформа на раннем этапе (нет production), **запрещено создавать новые миграции для исправления старых**.

- Если нужно добавить поле в `cat_counterparties`, редактируйте существующий файл `00006_cat_counterparties.sql`.
- `make reset-db` отсутствует. Проверяйте исходные миграции на отдельной новой тестовой БД; пользовательские tenant-БД автоматически не пересоздаются. Перенос заполненного окружения выполняется явным операторским upgrade. См. [правила миграций](../../db/migrations/README.md).
- Для mutable business/configuration tables применяются `version`, `_txid`, `_deleted_at` и предусмотренные моделью audit/CDC triggers. Append-only регистры, projections, leases и auth-state имеют отдельный контракт. Время хранится как `TIMESTAMPTZ`.

## 7. Безопасность: сообщения об ошибках (CWE-209)

> [!IMPORTANT]
> Ошибки, возвращаемые клиенту, **не должны содержать** чувствительную информацию.

- **Запрещено** включать в `apperror.Validation` или `apperror.NotFound`:
  - Точные суммы балансов, комиссий, лимитов
  - Внутренние ID (кроме тех, что клиент сам прислал)
  - SQL-ошибки, stack traces, имена таблиц
  - Количество записей, метрики системы

- **Правильный паттерн:**
  ```go
  // ❌ Утечка баланса
  apperror.NewValidation(fmt.Sprintf("insufficient balance: available %d, requested %d", avail, req))

  // ✅ Generic сообщение + серверный лог
  logger.Warn("insufficient balance", "available", avail, "requested", req, "merchant_id", mid)
  return apperror.NewValidation("insufficient balance")
  ```

- Детали логируются **только на сервере** через structured logging (`logger.Warn`/`logger.Error`) для диагностики.
- Это распространяется на все финансовые операции: балансы, комиссии, лимиты, курсы.

## 8. Документ: привязка ID

> [!WARNING]
> ID документа **всегда** генерируется на стороне Go (`id.New()`) и передаётся в INSERT.

- Запрещено использовать `DEFAULT gen_random_uuid()` для документов, участвующих в проведении (Posting Engine). Движения (`reg_*_movements`) записываются с тем же UUID, что и документ — его нельзя генерировать на стороне БД.
- При обходе `BaseDocumentRepo.Create()` (например, custom SQL в `portal_repo`) — ID обязателен как параметр.
