# Конечная проверка P3

P3 завершается по этой таблице и поимённому индексу путей записи. Номера технических проходов не являются процентом готовности. Список фиксирует существующий код; новые функции P4–P12 проверяются в своих этапах. Рабочая БД для приёмки P3 не изменяется.

|---|---|---|---|
| P3-R1 | ExternalOutflowService.Classify/Resolve/ApproveAdjustment/RejectAdjustment; ExternalOutflowWorkflowRepo и SQL decision guards | Полный actor/reason/evidence/basis replay, неизменяемая история, отсутствие второго проведения/снятия hold; legacy без основания не получает выдуманное решение | Закрыто на этапе 111; профильные и полные crypto suites прошли |
| P3-R2 | ObservedExternalOutflowRepo.UpsertExternalOutflow, ExternalOutflowIncidentRepo.UpsertExternalOutflowIncident, HasFalsePositiveProof и ResolutionReadiness | Закрытый случай и повторное появление имеют отдельные основания; позднее сообщение не превращает прежнее решение в разрешение нового действия | Открыто |

Снимок этапа 111 / схема 104: [Go-индекс](crypto-p3-go-paths.csv) содержит 1777 кандидатов, [SQL-индекс](crypto-p3-sql-paths.csv) — 654 фактических публичных функций/процедур. Эти числа не являются количеством требуемых исправлений. Чистые чтения и неприменимые ERP-механизмы входят в консервативный список и требуют явной классификации. [Журнал проверок](crypto-p3-review.csv) фиксирует 21 проверенную в рамках R1 функцию и её hash; отсутствие строки означает отсутствие отметки о проверке, а не автоматическое подтверждение.

Индекс Go формируется `go run ./cmd/crypto-p3-inventory`. Он включает прямую запись SQL, вызовы SQL-функций и команд/блокировок в участвующих пакетах. Это консервативный перечень кандидатов, а не список обнаруженных ошибок: чистые функции и пути вне P3 помечаются явно при проверке. Для каждого тела записан SHA-256, чтобы изменение уже проверенной функции требовало повторной оценки. SQL-индекс получен [read-only запросом](crypto-p3-inventory.sql) из `pg_proc`/`pg_trigger` свежей одноразовой БД схемы 104. В нём сохранены hash определений, сигнатуры и привязки/состояние triggers. Исторические заменённые определения миграций в этот снимок не входят. При изменении тела функции или trigger binding прежняя отметка требует повторной проверки.

Проверка строки означает подтверждение четырёх пунктов: неизменяемое основание или явно изменяемая проекция; правило повтора с полным payload; полный порядок ресурсов/полномочий; атомарность и целевой тест либо обоснование неприменимости. Новый найденный путь относится к существующему пакету P3-R1–R8 и пополняет индекс с объяснением. Новое хозяйственное поведение не добавляется в P3 без отдельного изменения плана.

[Manifest снимка](crypto-p3-inventory-manifest.json) фиксирует hash исходников cmd/internal/db, миграций и индексных артефактов.

P3 считается завершённым только при закрытии P3-R1–R8. Включение автоматического receipt intake, распределения, новых provider/refund возможностей и массовый перенос истории остаются P4–P12.


Проверки этапа 111: build, полный Go race, production/integration lint (0 issues), 436 contracts, TypeScript/ESLint; focused PostgreSQL/race 39 с; полный crypto_repo 729 с, TRON/EVM funding 45/4 с и worker 80 с на отдельных свежих БД схемы 104. Индексы воспроизводимы, 21 scoped R1 hash проверен. Временный PostgreSQL и runner удалены. Рабочая БД не обновлялась. Общий integration gate вне названных suites полностью зелёным не объявляется. R2–R8 остаются открытыми.
