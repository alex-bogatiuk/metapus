# Модуль 9. Управление Памятью, Профилирование и Производительность

> Учебные фрагменты сокращены и показывают отдельный принцип; полный актуальный код открывайте по указанным исходникам. Примеры Item/Product и товарных документов не означают наличия этих модулей в текущем контенте.

> В 1С программист крайне редко думает о том, где именно в оперативной памяти лежит ТаблицаЗначений. Платформа делает это за нас (и иногда "падает" с нехваткой памяти). В Go мы имеем полный контроль над памятью. Этот модуль объясняет, как писать код, который работает не просто быстро, а молниеносно.

---

## 1. Стек (Stack) vs. Куча (Heap)

Каждая программа на Go использует две области памяти: Стек и Кучу.

### Стек (Stack)
- **Что это:** Быстрая память, привязанная к конкретной горутине.
- **Как работает:** Вызывается функция — на стек кладётся «фрейм» (переменные). Функция завершается — фрейм мгновенно удаляется.
- **Скорость:** Мгновенная аллокация (просто сдвиг указателя) и нулевая стоимость очистки.
- **Garbage Collector:** Стек не сканируется сборщиком мусора!

### Куча (Heap)
- **Что это:** Общая память для всего приложения.
- **Как работает:** Если переменная должна "пережить" функцию (например, вы возвращаете указатель на неё), она «убегает» (escapes) в кучу.
- **Скорость:** Аллокация требует поиска свободного места.
- **Garbage Collector:** Кучу нужно очищать. Это делает сборщик мусора (GC).

**Ваша задача как Go-разработчика:** минимизировать выделения памяти (аллокации) в куче!

### Escape Analysis (Анализ побега)

Компилятор Go сам решает, куда положить переменную. Это называется Escape Analysis.

```go
func noEscape() int {
    x := 42
    return x // Возвращаем ЗНАЧЕНИЕ. x удалится вместе со стеком. Аллокаций в куче: 0.
}

func escapes() *int {
    x := 42
    return &x // Возвращаем УКАЗАТЕЛЬ. x "переживёт" функцию.
              // Компилятор перенесёт x в КУЧУ. Аллокаций в куче: 1.
}
```

> [!TIP]
> **Как посмотреть, что убежало в кучу:**
> Запустите сборку с флагом `-m`:
> `go build -gcflags="-m" ./cmd/server`
> Компилятор выдаст лог: `x escapes to heap` или `make([]int) escapes to heap`.

## 2. Garbage Collector (GC)

В Go встроен сборщик мусора. Он работает параллельно с вашей программой и периодически очищает кучу от объектов, на которые больше нет ссылок.

В Java или C# GC часто вызывает долгие "Stop-The-World" (STW) паузы, когда всё приложение замирает на секунды. 
**В Go GC оптимизирован на минимальные задержки.** STW-паузы в Go обычно составляют **доли миллисекунды**.

**Но есть цена:** GC потребляет CPU. Чем больше мусора (объектов в куче) вы генерируете, тем больше CPU уйдёт на работу GC, а не на полезную бизнес-логику.

> [!CAUTION]
> **Золотое правило производительности Go:**
> Меньше указателей — быстрее работает GC. Сборщику мусора нужно «обойти» каждый указатель, чтобы понять, живой объект или нет. Если у вас слайс из миллиона структур `[]Item` — GC обойдёт его мгновенно. Если слайс указателей `[]*Item` — GC будет сканировать каждый из миллиона указателей!

## 3. Capacity Hints (Правило §3)

Мы упоминали это в Модуле 1, но теперь вы понимаете физику процесса.

```go
// ❌ ПЛОХО: 
var items []string
for i := 0; i < 1000; i++ {
    items = append(items, "test")
}
```
**Что происходит:** Слайс `items` начинает с размера 0. При `append` Go выделяет память на 1 элемент. Потом на 2. Потом на 4, 8, 16... Каждый раз Go выделяет **новый блок в куче**, копирует старые данные, а старый блок оставляет как мусор для GC!

```go
// ✅ ПРАВИЛЬНО:
items := make([]string, 0, 1000) // сразу выделили кусок на 1000 элементов
for i := 0; i < 1000; i++ {
    items = append(items, "test")
}
```
**Итог:** Ровно ОДНА аллокация памяти. Работает в десятки раз быстрее.

## 4. Бенчмарки (Benchmarks)

В 1С вы меряете скорость через `ТекущаяУниверсальнаяДатаВМиллисекундах()`. В Go есть встроенный механизм микро-бенчмарков!

Файл `math_test.go`:
```go
func BenchmarkAppendBad(b *testing.B) {
    // b.N — количество итераций, Go сам подберёт нужное число (от 1 до миллиардов)
    for i := 0; i < b.N; i++ {
        var items []int
        for j := 0; j < 1000; j++ {
            items = append(items, j)
        }
    }
}

func BenchmarkAppendGood(b *testing.B) {
    for i := 0; i < b.N; i++ {
        items := make([]int, 0, 1000)
        for j := 0; j < 1000; j++ {
            items = append(items, j)
        }
    }
}
```

Запуск с флагом `-benchmem` (показать память):
```bash
go test -bench=. -benchmem
```

Результат поражает:
```
BenchmarkAppendBad-8    319363      3665 ns/op    25208 B/op     12 allocs/op
BenchmarkAppendGood-8  1421008       835 ns/op     8192 B/op      1 allocs/op
```
- Хороший вариант в 4 раза быстрее (835 наносекунд против 3665).
- Хороший вариант делает 1 аллокацию (1 allocs/op), плохой — 12 аллокаций.

## 5. Профилирование с помощью pprof

Если ваш бэкенд тормозит (или ест много памяти), не нужно гадать. Go имеет встроенный профайлер `pprof`.

Metapus (если включить нужный роут) может отдавать профиль прямо по HTTP.

**Шаг 1. Сбор профиля CPU (за 30 секунд):**
```bash
go tool pprof http://localhost:8080/debug/pprof/profile?seconds=30
```

**Шаг 2. Сбор профиля памяти (куча):**
```bash
go tool pprof http://localhost:8080/debug/pprof/heap
```

Утилита откроет интерактивную консоль. Команды:
- `top` — топ-10 функций, которые едят CPU или память.
- `list <ИмяФункции>` — покажет исходный код вашей функции и время/память, потраченное **на каждой строке**!
- `web` — откроет красивый граф вызовов в браузере (требует установленного Graphviz).

> [!IMPORTANT]
> **Это суперсила Go.** Вы можете подключиться к продакшен-серверу под нагрузкой, снять профиль за 30 секунд и найти строку кода, которая тормозит всю систему, не останавливая сервер.

## 6. Линтеры и статический анализ

В 1С есть механизм проверки модулей. В Go экосистема линтеров огромна.

### go vet
Встроенный анализатор, который находит подозрительные конструкции (ошибки в `Printf`, недостижимый код):
```bash
go vet ./...
```

### golangci-lint
Это мега-линтер, объединяющий десятки проверок (от неиспользуемых переменных до цикломатической сложности). 

Запуск в проекте Metapus:
```bash
golangci-lint run ./...
```
*Наш CI-пайплайн настроен так, что код не попадёт в главную ветку (main), пока линтер не будет полностью "зелёным".*
