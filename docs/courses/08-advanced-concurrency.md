# Модуль 8. Продвинутая многозадачность (Advanced Concurrency)

> Учебные фрагменты сокращены и показывают отдельный принцип; полный актуальный код открывайте по указанным исходникам. Примеры Item/Product и товарных документов не означают наличия этих модулей в текущем контенте.

> Этот модуль для тех, кто хочет понимать, как работают высоконагруженные части Metapus (например, воркеры блокчейна или фоновые рассылки). В 1С параллелизм ограничен фоновыми заданиями. В Go мы можем тонко управлять горутинами, защищать данные и распараллеливать вычисления.

## 1. Защита данных: sync.Mutex

В 1С (при работе на сервере) к объекту в памяти обычно обращается один поток. В Go **сотни горутин могут одновременно читать и писать одну и ту же переменную**. Если они сделают это без защиты, произойдёт **Data Race (гонка данных)** — и данные сломаются.

Для защиты используется **Мьютекс** (Mutex — Mutual Exclusion, взаимное исключение).

```go
import "sync"

type Counter struct {
    mu    sync.Mutex
    value int
}

func (c *Counter) Increment() {
    c.mu.Lock()         // 🔒 Блокируем доступ для других горутин
    defer c.mu.Unlock() // 🔓 Обязательно разблокируем при выходе

    c.value++           // Безопасное изменение
}

func (c *Counter) Value() int {
    c.mu.Lock()
    defer c.mu.Unlock()
    return c.value
}
```

> [!WARNING]
> **Золотое правило:** ВСЕГДА используйте `defer mu.Unlock()`. Если внутри функции произойдёт ошибка (или panic) и вы забудете вызвать `Unlock()`, все остальные горутины, ждущие `Lock()`, зависнут навсегда (Deadlock).

### sync.RWMutex — разделение на чтение и запись

Обычный `Mutex` блокирует всех. Но если у нас 99% времени данные только читаются, обычный лок будет тормозить систему. Для этого есть `RWMutex`:

```go
type Cache struct {
    mu   sync.RWMutex
    data map[string]string
}

// Запись (эксклюзивная блокировка) — никто не может ни читать, ни писать
func (c *Cache) Set(key, val string) {
    c.mu.Lock()
    defer c.mu.Unlock()
    c.data[key] = val
}

// Чтение (разделяемая блокировка) — могут читать тысячи горутин одновременно!
// Но если кто-то захочет сделать Set() — он будет ждать, пока все читатели не закончат.
func (c *Cache) Get(key string) string {
    c.mu.RLock()         // RLock - блокировка для чтения
    defer c.mu.RUnlock() // RUnlock - снятие блокировки для чтения
    return c.data[key]
}
```

## 2. sync.Once — ленивая инициализация

Иногда нужно, чтобы кусок кода выполнился **строго один раз**, даже если его вызывают одновременно 100 горутин. В 1С мы бы писали блокировки БД. В Go есть `sync.Once`:

```go
var (
    once     sync.Once
    settings map[string]string
)

func loadSettings() {
    once.Do(func() {
        // Этот код выполнится ТОЛЬКО ОДИН РАЗ, 
        // независимо от того, сколько горутин вызовут loadSettings()
        fmt.Println("Инициализация настроек...")
        settings = map[string]string{"theme": "dark"}
    })
}

func main() {
    go loadSettings()
    go loadSettings()
    go loadSettings()
    // В консоли будет только одна строка "Инициализация настроек..."
}
```

## 3. Паттерн: Worker Pool

Представьте: вам нужно обработать 100 000 строк из файла. Если запустить 100 000 горутин — база данных «ляжет» от количества подключений.
Решение: **Worker Pool**. Мы создаём фиксированное число горутин (например, 10), которые берут задачи из общего канала.

```go
func worker(id int, jobs <-chan int, results chan<- int) {
    for j := range jobs {
        fmt.Printf("Воркер %d начал задачу %d\n", id, j)
        time.Sleep(time.Second) // имитация работы
        results <- j * 2
    }
}

func main() {
    const numJobs = 100
    jobs := make(chan int, numJobs)
    results := make(chan int, numJobs)

    // Запускаем 3 воркера (пул из 3 горутин)
    for w := 1; w <= 3; w++ {
        go worker(w, jobs, results)
    }

    // Отправляем 10 задач в очередь
    for j := 1; j <= 10; j++ {
        jobs <- j
    }
    close(jobs) // закрываем канал — сигнал воркерам, что задач больше нет

    // Собираем результаты
    for a := 1; a <= 10; a++ {
        <-results
    }
}
```

> [!TIP]
> **Где это в Metapus:**
> Воркеры обработки блокчейна (пакет `internal/infrastructure/blockchain`) используют именно этот паттерн. Пул воркеров читает блоки из Tron, а фиксированное количество горутин обрабатывает транзакции, чтобы не перегрузить базу данных.

## 4. ErrGroup — параллельное выполнение с контролем ошибок

`sync.WaitGroup` отличная вещь, но она не умеет собирать ошибки. Если 3 горутины скачивают файлы, и одна упала — как узнать об этом?

Для этого в Go есть пакет `golang.org/x/sync/errgroup`:

```go
import "golang.org/x/sync/errgroup"

func fetchAll(urls []string) error {
    var g errgroup.Group

    for _, url := range urls {
        url := url // Важно! Копируем переменную цикла (для Go < 1.22)
        
        g.Go(func() error {
            // Скачиваем url
            resp, err := http.Get(url)
            if err != nil {
                return err // Ошибка вернётся в g.Wait()
            }
            defer resp.Body.Close()
            return nil
        })
    }

    // Wait блокирует, пока ВСЕ горутины не завершатся.
    // Если хоть одна вернула ошибку — Wait() вернёт её!
    if err := g.Wait(); err != nil {
        return fmt.Errorf("ошибка при скачивании: %w", err)
    }
    return nil
}
```

**Ещё круче:** `errgroup.WithContext(ctx)`. Если одна горутина падает, `errgroup` автоматически **отменяет контекст** для всех остальных! Это идеальный fail-fast механизм.

## 5. Паттерн Fan-Out / Fan-In

- **Fan-Out (Разветвление):** Несколько горутин читают из одного канала (Worker Pool).
- **Fan-In (Слияние):** Одна горутина читает из НЕСКОЛЬКИХ каналов и пишет в один результатирующий.

```go
func fanIn(ch1, ch2 <-chan string) <-chan string {
    out := make(chan string)
    
    go func() {
        for {
            select {
            case msg1 := <-ch1:
                out <- msg1
            case msg2 := <-ch2:
                out <- msg2
            }
        }
    }()
    
    return out
}
```

В 1С это было бы похоже на объединение результатов нескольких фоновых заданий в одну таблицу значений, но в реальном времени.

## 6. Детектор гонок (Race Detector)

Самый страшный баг в Go — Data Race (состояние гонки). Он возникает, когда две горутины обращаются к переменной, и хотя бы одна из них ПИШЕТ. Симптомы: программа работает на локальном ПК, но падает в продакшене с непонятными ошибками раз в неделю.

Go имеет встроенный инструмент поиска гонок. Просто добавьте флаг `-race`:

```bash
# Запуск тестов с детектором гонок
go test -race ./...

# Запуск сервера локально с детектором гонок
go run -race ./cmd/server
```

Если Go обнаружит гонку, он выведет ОГРОМНЫЙ красный лог:
```
==================
WARNING: DATA RACE
Write at 0x00c000102008 by goroutine 7:
  main.worker()
...
Read at 0x00c000102008 by goroutine 6:
  main.main()
==================
```
Это означает, что вам нужно добавить `sync.Mutex` или переделать логику на использование каналов.
