# Учётные записи интеграций

> **TL;DR:** Аккаунты, постоянные ключи, состав пулов и состояния квот находятся в БД тенанта. Пулы подключаются к RPC и CoinGecko; изменения перечитываются без перезапуска.
> **Тип:** Runbook
> **Аудитория:** Admin, Developer
> **Связанные:** [RPC ingestion](rpc-ingestion.md), [Курсы валют](../systems/exchange-rates.md)

## Настройка

В «Справочники → Интеграции» создайте учётную запись для каждого внешнего аккаунта. Сначала выберите назначение («Доступ к блокчейну — RPC» или «Курсы валют»), затем провайдера. После выбора появятся наименование, реквизиты доступа и настройки квоты. Провайдер по умолчанию не выбирается. Несколько ключей одной подписки — именованные ключи одной записи, например `sepolia` и `mainnet`. Они расходуют общую квоту аккаунта.

Каждый API-ключ может принадлежать только одному не помеченному на удаление аккаунту того же провайдера в БД тенанта. Совпадение хотя бы одного ключа, в том числе под другим именем, отклоняет создание, изменение или импорт с HTTP 409 и сообщением «Ключи уже используются в аккаунте „Наименование“ (Код)». Отключение аккаунта не освобождает его ключи. После удаления ключей или пометки аккаунта на удаление их можно перенести; восстановление старого аккаунта повторно проверяет уникальность. Совпадения у разных провайдеров или тенантов независимы.

Проверка выполняется в репозитории в одной транзакции с записью под общей блокировкой конфигурации интеграций. Ключи сравниваются после расшифровки только в памяти; шифротексты AES-GCM не подходят для сравнения из-за случайного nonce. Одним запросом читаются ключи остальных аккаунтов данного провайдера, поэтому стоимость проверки зависит от их количества и возникает только при изменении справочника. Миграция, пересохранение существующих ключей и изменение runtime-запросов не требуются. Ранее сохранённые дубли автоматически не объединяются: перенесите ссылки на нужный аккаунт и удалите лишние ключи или пометьте лишний аккаунт на удаление.

Назначения, доступные провайдеры, профили ключей и политика квоты описаны единым серверным реестром. Его read API — `GET /api/v1/system/integrations/providers`; доступ определяется существующими правами чтения, создания или изменения аккаунтов/пулов. Назначение не хранится отдельным реквизитом аккаунта и не создаёт новую квоту. Один профиль может поддерживать несколько назначений. Ссылку на создание можно дополнить `?kind=rpc` или `?kind=exchange_rates`; провайдер и в этом случае выбирается явно.

При смене назначения или провайдера в новой карточке введённые ключи очищаются только после подтверждения. Наименование и прочие общие реквизиты сохраняются. В сохранённой карточке назначение определяется провайдером. Старые Telegram, SMTP и API ресурсов доступны для просмотра и правки, но создание новых аккаунтов и пулов этих профилей через общий механизм закрыто до подключения соответствующих потребителей. Уведомления и поставщики ресурсов продолжают настраиваться в своих подсистемах.

В списках аккаунтов и пулов доступны колонка и фильтр «Назначение». Фильтр преобразуется в условие по провайдерам и применяется на сервере до подсчёта и пагинации. В форме пула используется тот же выбор «Назначение → Провайдер»; пул по-прежнему содержит аккаунты только одного провайдера.

Создайте пул одного провайдера и расположите аккаунты в порядке использования. В подключении RPC укажите сеть, роль, независимую группу провайдера, адрес без ключа и пул. Для Alchemy адрес имеет вид `https://eth-sepolia.g.alchemy.com/v2/`, группа — `alchemy`. Публичный RPC подключается без пула; имя ключа у него не используется.

«Имя ключа» выбирает, какой именованный ключ выбранного аккаунта пула читает подключение. Если имя однозначно задано профилем провайдера (Infura, dRPC и Chainstack по сети, GetBlock по роли), форма показывает его только для чтения, а сервер подставляет его вместо пустого значения или `default`. Для Alchemy форма предлагает список имён, которые есть во всех аккаунтах пула с заданными ключами. Сервер отклоняет подключение, состав пула и замену ключей аккаунта, если в аккаунте с ключами нет имени, которое читает подключение этого пула. Аккаунты без ключей в этой проверке не участвуют. Если отсутствие ключа всё же обнаружено при работе, статус RPC показывает причину `pool_key_missing`. Несколько аккаунтов Alchemy дают один голос при проверке canonical/quorum.

Для сети выберите источник RPC `database`. При `file` продолжает действовать прежний `CRYPTO_CHAIN_CONFIG_FILE`. Переведённая в `database` сеть при ошибке не возвращается к файловым ключам. Связь с CoinGecko задаётся полем «Пул аккаунтов» существующего источника курсов; mappings и история котировок сохраняются.

### Alchemy: EVM и TRON

Один провайдер Alchemy поддерживает EVM execution RPC и native HTTP API TRON.
Для TRON Nile используйте базовый URL `https://tron-testnet.g.alchemy.com/v2/`,
для TRON Mainnet — `https://tron-mainnet.g.alchemy.com/v2/`. Сеть задаётся явно:
`nile` или `mainnet`. Точные TRON hosts имеют приоритет перед общим EVM
суффиксом `.g.alchemy.com`; назначить их EVM-сети нельзя.

Создайте две привязки с ролями `fullnode` и `solidity`, одним пулом и именем
ключа, например `nile`. Группа доверия обеих привязок — `alchemy`. Базовый URL
сохраняется без ключа и пути метода. Клиент добавляет `/wallet/...` либо
`/walletsolidity/...`, а HTTP-профиль вставляет ключ после `/v2/` только в копию
исходящего запроса. TronGrid V1 indexer этим профилем не поддерживается.
Несколько ключей одной подписки используют общую запись аккаунта и её квоту.

До проверки включите нужную сеть в приложении Alchemy. Ответ HTTP 403
`is not enabled for this app` означает отсутствие доступа к конкретной сети:
он возвращает безопасную ошибку операции и не помечает общий ключ аккаунта
неверным. Ошибки credentials и исчерпание квоты по-прежнему обрабатываются
общим transport. Для каждой TRON-роли требуется минимум два независимых
оператора; несколько аккаунтов Alchemy дают только один голос.

### Порядок и отключение RPC через UI

На странице «Администрирование → Криптовалютные сети» блок «RPC-подключения» показывает подключения конкретной сети, порядок по ролям и последнее состояние. Для изменения нужны права чтения сети, чтения и обновления `crypto_rpc_endpoint`; штатное подтверждение чувствительного действия сохраняется. Ограничения доступа к строкам и полям применяются также к новому API.

Нажмите «Настроить RPC». Переключатель «Использовать» исключает подключение из новой конфигурации, сохраняя запись, ключи и пул. Кнопки «Выше / Ниже» меняют порядок только внутри одной роли. «Применить RPC» сохраняет весь набор изменений одной транзакцией; «Отменить» сбрасывает черновик. При параллельном изменении загрузите актуальные настройки. После неоднозначного сетевого ответа повторяется тот же запрос с тем же ключом идемпотентности.

Для возврата включите «Показывать отключённые», откройте настройку RPC, включите запись и примените изменения. Отключение одной привязки Chainstack не изменяет подключения других сетей и не сбрасывает квоты общего аккаунта. Сервер запрещает уменьшать необходимое покрытие ролей и независимых операторов. Несколько подключений/аккаунтов одного сервиса не дают дополнительные независимые голоса.

Порядок определяет предпочтение при начальном выборе; действующие sticky routing, recovery и quorum продолжают учитывать доступность и тип операции. Состояние «Запросы приостановлены» относится к автоматической защите. «Отключён администратором» сохраняется до ручного включения. Разверните диагностику строки, чтобы увидеть безопасную причину и текущую серию ошибок по методам.

Сохранение и применение различаются. RPC-конфигурация перечитывается при обращениях с интервалом 10 секунд, воркер публикует снимок раз в 30 секунд, страница обновляет данные раз в 15 секунд. Совпадение ревизии подтверждает применение наблюдаемым воркером; один снимок не подтверждает все процессы. Новая generation обслуживает новые операции без выключенного endpoint; старые операции используют существующие правила завершения. Изменение порядка создаёт новую generation с новыми circuits и предпочтениями, а состояния аккаунтов и квот сохраняются.

Для `rpcConfigSource=file` доступен просмотр. Перенос в БД выполняется отдельно по этой инструкции; экран не переключает режим автоматически. URL, ключи, пул и роль редактируются в справочнике «Подключения RPC».

API: `GET` и `PATCH /api/v1/admin/crypto/networks/:networkId/rpc-configuration`. Формат команд зарегистрирован в HTTP-контрактах. Новые колонки и миграция для управления активностью/порядком не требуются; metadata runtime добавляется в существующий JSONB-массив.

### Ankr Freemium для Ethereum Sepolia

Для создания аккаунта и пула значение `ankr` должно входить в ограничения `ck_integration_accounts_provider` и `ck_integration_pools_provider`. Для новой tenant-БД достаточно штатной миграции. При обновлении существующей БД с уже применённой `00006` замените оба ограничения в одной транзакции, используя два определения `ADD CONSTRAINT` из [crypto_core](../../db/configuration/crypto/00006_crypto_core.sql).

1. В «Справочники → Интеграции» создайте аккаунт с назначением «Доступ к блокчейну — RPC» и провайдером **Ankr**. В поле «Ключ Ankr» вставьте ключ проекта или полную HTTPS-ссылку Sepolia из кабинета Ankr. Форма извлечёт ключ в слот `sepolia`. Укажите день и часовой пояс обновления месячной квоты по вашему аккаунту.
2. Добавьте аккаунт в пул Ankr. В справочнике «Подключения RPC» создайте активное подключение сети Ethereum Sepolia с ролью `rpc`, базовым адресом `https://rpc.ankr.com/eth_sepolia`, группой доверия `ankr` и этим пулом. Все подключения Ankr дают один голос при проверке блока.
3. В карточке пула нажмите «Проверить подключение». Metapus отправит `eth_chainId` и сверит ответ с `0xaa36a7` (11155111). Для использования привязки воркерами источник RPC сети должен быть `database`.

Freemium предоставляет 200 млн кредитов в месяц. Metapus выдерживает интервал от 34 мс между запросами одного аккаунта внутри процесса. HTTP 429 и код `-32090` временно приостанавливают аккаунт с учётом `Retry-After`. Запрет отдельного метода сохраняет доступ аккаунта к остальным методам. [Тарифы Ankr](https://www.ankr.com/docs/rpc-service/service-plans/) · [Ошибки RPC](https://www.ankr.com/docs/rpc-service/errors/overview/)

### Validation Cloud, ZAN и Uniblock

Создайте аккаунт и пул выбранного провайдера в справочнике интеграций. В карточке RPC-подключения укажите пул и базовый URL из таблицы. Для существующей tenant-БД обновите оба ограничения списка провайдеров по инструкции выше.

| Провайдер | Сеть | Роль | Базовый URL | Имя ключа | Группа доверия |
|---|---|---|---|---|---|
| Validation Cloud | Ethereum Sepolia | `rpc` | `https://sepolia.ethereum.validationcloud.io/v1` | `sepolia` | `validation_cloud` |
| ZAN | Ethereum Sepolia | `rpc` | `https://api.zan.top/node/v1/eth/sepolia` | `default` | `zan` |
| ZAN | TRON Nile | `fullnode`, `solidity` | `https://api.zan.top/node/v1/tron/nile` | `default` | `zan` |
| Uniblock | Ethereum Sepolia | `rpc` | `https://api.uniblock.dev/uni/v1/json-rpc` | `default` | `uniblock` |

В карточку аккаунта Validation Cloud или ZAN можно вставить полную ссылку из кабинета. Для ZAN подойдёт и ссылка Nile с окончанием `/jsonrpc`. Один ключ и пул ZAN обслуживают обе сети. Для Nile создайте по одному подключению каждой роли. Драйвер сам добавляет к запросам пути `wallet` и `walletsolidity`. Для бесплатного пакета ZAN сверяйте настроенную дату сброса с очередным 30-дневным циклом в кабинете. [Документация ZAN](https://docs.zan.top/docs/new-credit-costs)

Для Uniblock введите ключ проекта. Транспорт отправляет его в заголовке `x-api-key` и добавляет `chainId=11155111` к исходящему запросу. Uniblock предоставляет для TRON интерфейс JSON-RPC с методами `eth_*`. Роли TRON в Metapus требуют нативного HTTP API. [TRON Mainnet](https://docs.uniblock.dev/reference/jsonrpc/tron/tron-protocol-overview) · [TRON Testnet](https://docs.uniblock.dev/reference/jsonrpc/tron-testnet/tron-testnet-overview)

### Infura Ethereum Sepolia

Создайте аккаунт провайдера `infura`, введите именованный ключ `sepolia`:
32 шестнадцатеричных символа из HTTPS URL Infura. Форма принимает также полную
ссылку Sepolia и извлекает ключ в оперативной памяти. Ключ шифруется в БД аккаунта.
В пуле Infura разместите аккаунты одной подписки; дополнительные ключи одного
аккаунта не дают отдельную квоту или независимый голос.

RPC-привязка: `https://sepolia.infura.io/v3/` без ключа, сеть Sepolia
(`11155111`), роль `rpc`, группа доверия `infura`, слот `sepolia` и пул этого
провайдера. Ключ подставляется только в исходящий запрос; чужие hosts, URL с
ключом/query/userinfo и другие сети этим профилем не принимаются. Все Infura
подключения дают один голос quorum. Проверка доступа требует точный chain ID.

По [документации Infura](https://docs.infura.io/how-to/avoid-rate-limiting/)
квота суточная и обновляется в 00:00 UTC. HTTP 402 временно исключает аккаунт
до следующего UTC дня, затем используется следующий аккаунт/провайдер. HTTP 429
учитывает Retry-After, HTTP 401/403 отключает текущую версию ключа. Число
запросов не считается точным остатком credits: стоимость зависит от метода.
Account pacer Infura ограничивает каждый процесс до 1 RPS; общий бюджет всех процессов
нужно соотносить с тарифом. Месячный день оплаты для Infura не задаёт период квоты.

Перед активацией проверьте свежие и исторические headers, полные blocks,
receipts и logs штатным `crypto-preflight -mode rpc`.

### Chainstack TRON Nile

Создайте отдельную запись provider `chainstack` для каждого внешнего аккаунта с независимой квотой. Введите именованный ключ `nile`: только токен из HTTP URL Chainstack, без полного URL, суффиксов API и пробелов. Username/Password и gRPC для этого профиля не используются. Период квоты задаётся для каждого аккаунта по его Billing/Usage.

В пуле `CHAINSTACK-NILE` расположите аккаунты в порядке использования. Создайте два RPC-подключения с общей базой `https://tron-nile.core.chainstack.com`, ролями `fullnode` и `solidity`, группой доверия `chainstack`, одним пулом и слотом `nile`. Пути `/wallet/...` и `/walletsolidity/...` формирует клиент; токен добавляется только в исходящий запрос. Команда проверки доступа использует фактическую роль действующей RPC-привязки.

Поддерживаются native HTTP API TRON Nile и execution JSON-RPC Ethereum Sepolia. Для Sepolia используйте отдельный аккаунт с ключом `sepolia`, пул `CHAINSTACK-SEPOLIA` и RPC-привязку `https://ethereum-sepolia.core.chainstack.com`, роль `rpc`, слот `sepolia`, группу доверия `chainstack`. При общей внешней подписке нескольких сетей её квота учитывается одной записью аккаунта с именованными ключами; отдельные подписки сохраняются отдельными аккаунтами. Beacon, WSS и Basic Auth этим профилем не используются. Проверка доступа Sepolia запрашивает `eth_chainId` и требует `11155111`. Для активных привязок одного аккаунта минимальный интервал запросов должен совпадать. Чтобы изменить сразу несколько привязок, можно временно отключить их, установить одинаковое значение и включить вновь.

Managed transport применяет интервал не менее 200 мс и burst=1: до 5 RPS на аккаунт в одном процессе, совместно для слотов, пулов и поколений клиентов. При увеличении числа процессов пересчитайте суммарный бюджет 25 RPS. Ротация аккаунтов повышает месячную ёмкость, сохраняя лимит скорости текущего аккаунта. Для 429 учитываются `Retry-After` либо `error.data.try_again_in` с jitter; неоднозначный 403 не объявляется месячным исчерпанием или заведомо неверным ключом.

Переключение выполняется в два уровня: следующий доступный аккаунт текущего пула, затем следующий RPC-провайдер по существующим приоритетам. Недоступность пула передаётся типизированной ошибкой; доступность повторно проверяется с учётом интервала конфигурации. Метрики `integration.http.requests` и `integration.http.responses` учитывают реальные HTTP-попытки и безопасные коды ответа. Секретные URL и тела ответов в метрики не включаются.

Для блока требуются два независимых оператора: например, TronGrid + Chainstack, а при недоступности пула — TronGrid + Nileex после успешного preflight. При замене стороны повторяется незавершённая целая проверка. Расхождение данных останавливает проверку и не обходится подбором третьего источника. При недостатке независимых источников checkpoint ожидает восстановления. Все аккаунты Chainstack представляют один голос, включая shadow.

[Каноническая нормализация TRON receipts](tron-block-ingestion.md#каноническая-нормализация-receipts) сверяет обязательные данные перевода и сохраняет отличия допустимых resource/voting traces в source digests. Неизвестный note, пропущенный обычный перевод или отличие денежных данных блокируют проверку.

Аккаунты и пулы доступны администраторам по исходным правам. Делегирование выполняется существующей моделью `catalog:integration_account:*`, `catalog:integration_pool:*`, `catalog:crypto_rpc_endpoint:*`. Изменения требуют штатного step-up. Ключи в GET, списках, metadata и exports отсутствуют. В форме значения вводятся заново только при замене; очистка — отдельное явное действие. Значения не сохраняются в браузерных черновиках.

## dRPC Sepolia: ручное продление

Выберите назначение RPC и провайдера dRPC. Поддерживается execution JSON-RPC Ethereum Sepolia (`11155111`), одна запись с ключом `sepolia`. Поле принимает токен или HTTPS-ссылку `lb.drpc.live/sepolia/<key>`; в API отправляется только токен. В RPC-подключении сохраняются базовый URL `https://lb.drpc.live/sepolia/`, пул, slot `sepolia` и группа доверия `drpc`. Все подключения dRPC представляют один голос.

При создании укажите ключ и будущую дату в поле «Действует до (UTC)». Поле редактирует UTC; сохранённый момент дополнительно показан в часовом поясе браузера. Дату назначает оператор; она не извлекается из токена.

В точности в момент окончания аккаунт перестаёт выбираться. Уже выбранный ключ не обходит срок через 10-секундный кэш, ожидание admission или retry: запрос ограничен credential deadline. Истечение не считается отказом исправного RPC-узла. В статусе нет даты автоматического сброса (`nextResetAt=null`). Начало месяца, включение аккаунта и команда «Возобновить» не продлевают ручной период. Подтверждённое исчерпание периода также сохраняется до продления, включая поздние успешные ответы.

Нажмите «Продлить ключ…», введите **новый ключ и новую будущую дату** и запишите карточку. Сервер сравнивает текущий расшифрованный токен, проверяет entity version и атомарно сохраняет ciphertext, срок и новое поколение ручного периода. Одинаковый ключ, только дата или только ключ отклоняются. Отмена возвращает сохранённый срок и очищает введённый секрет. После истечения разрешено менять имя и активность без повторного ввода ключа. Удаление ключа не создаёт новый период.

HTTP 429 означает временное ограничение; отдельный дневной лимит ключа блокирует до следующего UTC-дня в пределах срока. Подтверждённые billing/quota коды блокируют ручной период. Распознанное ограничение диапазона logs возвращается как `query_limit`; оно не делает ключ неверным и не означает исчерпание аккаунта. Минимальный интервал аккаунта — 200 мс, общий для его привязок внутри процесса; межпроцессного точного CU-счётчика нет.

CLI import требует `credentialsExpiresAt` в mapping и отдельный secret file ключа. Повторный импорт с другой датой отклоняется; продление выполняйте через карточку аккаунта. Значения ключей не выводятся в API, аудит и диагностические отчёты.

## Getblock.io TRON: ввод и замена токенов

В новой карточке выберите Getblock.io. Форма автоматически показывает «Токен FullNode REST» и «Токен Solidity REST» и назначает имена `fullnode` и `solidity`. Оба эндпоинта должны относиться к одной сети TRON и одному внешнему аккаунту. Пользователь не вводит имена ключей вручную.

Можно вставить токен или полную HTTPS-ссылку настроенного EU-эндпоинта `shared.eu-central-1.getblock.io`. Форма извлекает первый сегмент пути, проверяет адрес и суффикс REST-роли и отправляет только токен. Ссылки других регионов, с query/fragment, userinfo или неожиданным суффиксом отклоняются. По самому токену сеть и API-интерфейс не определяются. Проверка доступа выполняется в пуле с его фактической RPC-привязкой.

После записи значения скрываются. При обычной правке карточки credentials не передаются. Команда «Заменить оба токена…» открывает два пустых поля: текущий API заменяет весь набор, поэтому нужны оба значения. Сервер отклоняет неполную замену GetBlock. «Удалить все ключи…» требует подтверждения и применяется только после записи; до записи удаление можно отменить. Ключи у провайдера этим действием не отзываются.

После сохранения команда «Добавить в пул…» позволяет выбрать пул того же провайдера. Перед обновлением клиент читает актуальный состав и версию пула, добавляет аккаунт в конец списка и сохраняет остальные настройки. Уже добавленный аккаунт повторно не включается. Конкурирующее изменение защищено штатным optimistic locking; ошибка не приводит к перезаписи состава пула.

Провайдер сохранённой карточки фиксирован в интерфейсе. Для другого провайдера создайте отдельную запись. Служебный код находится в раскрываемом блоке. День и часовой пояс квоты сопровождаются предпросмотром следующего периода; для отсутствующих чисел используется последний день месяца. Ctrl/⌘+S записывает карточку, Ctrl/⌘+Shift+S записывает и закрывает её.

## Выбор и восстановление

Система сохраняет текущий аккаунт, пока он доступен. Подтверждённое месячное исчерпание исключает весь аккаунт до следующей границы периода. Обычный 429 означает временное ограничение с учётом Retry-After. Неверный ключ блокирует только его именованный слот текущей версии credentials. Замена ключей увеличивает эту версию; месячное исчерпание заменой ключа не снимается.

Курсор и состояния общие для worker и монитора данного тенанта. Запоздавшая ошибка прежнего выбора не перескакивает через уже выбранный следующий аккаунт. При новом периоде допускается один пробный запрос через короткий DB lease. Политика не прерывает здоровый текущий аккаунт только потому, что у другого обновилась квота.

На форме пула доступны ручное переключение, отметка исчерпания, разрешение повторной проверки и проверка доступа. Изменение состояния требует причины, expected selection version и Idempotency-Key; штатный клиент формирует ключ автоматически. Повтор после timeout не выполняет команду второй раз. Проверка доступа использует существующее RPC-подключение и его слот, если они настроены. Полную проверку сети/ролей выполняет существующий crypto preflight.

Настройки аккаунтов/пулов и RPC перечитываются каждые 10 секунд при обращениях. Существующие операции закрепляют RPC-клиенты до завершения; замена topology закрывает прежние соединения после освобождения последней ссылки. Ошибка нового EVM endpoint отражается его собственным статусом; wrong-chain endpoint не участвует в чтении. Удаление всех допустимых endpoints или недопустимая новая конфигурация останавливают новые операции.

При недоступности БД credential transport после истечения его 10-секундного cache прекращает новые запросы. Это строже предельных 60 секунд из плана. RPC topology может сохранять допустимый снимок до 60 секунд; восстановление квоты и новый выбор без БД не выполняются. Параметры watcher, включая TRON ingestion mode, меняются через штатный контролируемый перезапуск. Перезапуск для смены ключей и состава пулов не нужен.

Точный остаток внешней квоты не вычисляется. Process-local ограничения RPC сохраняются; распределённого token bucket нет. Если один внешний аккаунт используется вне данного тенанта, его внешняя квота также расходуется там.

## DNS локального стенда

DB RPC transport проверяет публичность всех DNS-адресов и закрепляет проверенный IP на время соединения. Если локальный VPN возвращает fake-IP из `198.18.0.0/15`, задайте только процессам API/worker/монитора и операторским RPC-проверкам `CRYPTO_RPC_DNS_TLS_SERVER=1.1.1.1:853`. RPC использует DNS-over-TLS с проверкой сертификата на указанный публичный IP. Резолвер должен быть задан IP-адресом с портом 853; приватные и служебные адреса запрещены. При ошибке резолвера запрос прекращается. Настройка не отключает SSRF-защиту, не меняет системный VPN и не требует сохранения IP провайдеров в конфигурации. Без переменной используется системный DNS.

## Перенос конфигурации из chains.json

Схема интеграций входит в миграции; существующие стенды пересоздаются с нуля, отдельного обновления схемы нет. Операторский инструмент `cmd/integration-config` переносит RPC и источники курсов из прежнего chains.json в БД. Он не меняет goose history, Meta-DB, финансовые документы, регистры или checkpoints.

1. Снимите штатный backup нужной tenant-БД и защищённые копии исходного chains.json и ключа шифрования. Убедитесь, что проверено восстановление backup.
2. Настройте `DATABASE_URL_FILE` именно этой tenant-БД. У app, worker и монитора должен быть одинаковый существующий 32-байтовый `AUTOMATION_ENCRYPTION_KEY_FILE`, хранящийся вне БД. Его потеря делает credentials нечитаемыми. Не указывайте секреты в CLI-аргументах.
3. Разверните новый backend/worker/монитор и frontend обычной процедурой. На этом одноразовом шаге требуется штатный перезапуск. До импорта RPC и источники курсов продолжают использовать прежнюю конфигурацию.
4. Подготовьте JSON-сопоставление без значений ключей. Ключи берутся из старого chains.json/секретных файлов и старого реквизита CoinGecko. Все секретные подключения требуют явного сопоставления внешнему аккаунту, чтобы разные ключи одной подписки не превратились в независимые квоты.

```json
{
  "ETHEREUM-SEPOLIA/rpc/alchemy-primary": {
    "externalAccountRef": "alchemy-account-a",
    "name": "Alchemy A",
    "poolCode": "ALCHEMY-SEPOLIA",
    "slot": "default"
  },
  "rateSource:COINGECKO": {
    "externalAccountRef": "coingecko-account-a",
    "name": "CoinGecko A",
    "poolCode": "COINGECKO-DEMO"
  }
}
```

Имена сети, провайдера и источника замените их действительными кодами. Для нескольких ключей одного аккаунта используйте одинаковый `externalAccountRef` и разные слоты. Account/pool provider должен быть совместим со всеми привязками.

```sh
go run ./cmd/integration-config --chains /secure/chains.json --mapping /secure/integration-mapping.json
go run ./cmd/integration-config --chains /secure/chains.json --mapping /secure/integration-mapping.json --apply
```

Сухой прогон выполняет те же проверки и откатывает транзакцию. Вывод содержит только счётчики. Применение сохраняет исходные priorities, keep-alive, интервалы, роли и family settings. Ключи шифруются до записи. Старый CoinGecko api_key очищается одновременно с установкой ссылки на пул; поэтому импорт выполняется после обновления worker. Повторный импорт не создаёт дубликаты и не перезаписывает вручную заменённые ключи или состав пула; конфликт требует явного согласования.

5. Проверьте импортированные аккаунты, период квоты и состав пулов. Добавьте остальные внешние аккаунты через формы. Проверьте доступ и запланируйте наблюдение за lag/готовностью. Включите DB mode по сетям через форму сети либо примените импорт с явным `--activate`:

```sh
go run ./cmd/integration-config --chains /secure/chains.json --mapping /secure/integration-mapping.json --apply --activate
```

6. Выполните существующий preflight и проверьте business progress native/token watchers, сохранность checkpoints и свежесть котировок. Отдельно проверьте переход на следующий аккаунт и сохранение состояния после штатного рестарта. Ручную отметку исчерпания снимайте только с осознанной причиной.
7. После подтверждения DB mode удалите действующие старые секретные монтирования и ненужные копии ключей по регламенту. Для оставшихся `file` сетей сохраните нужный файл. Не удаляйте ключ шифрования и необходимые backups.

## Откат

После очистки legacy CoinGecko api_key предыдущий worker без подготовки запускать нельзя: он не знает пулов. Предпочтительный откат — исправление DB-настроек и повторное развёртывание совместимого binary.

Явный возврат RPC сети в `file` использует только заранее проверенный актуальный файл. Он не должен обнулять сохранённые состояния квот или возвращать отозванный ключ. Наличие backup не доказывает действительность ключа у провайдера. Восстановление всей БД выполняется штатной процедурой с проверкой совместимости ledger/checkpoints; инструмент импорта не делает автоматический destructive rollback.

## Проверки реализации

Целевые Go race-тесты используют локальные HTTP/RPC mocks. Полный `go run ./cmd/integration-test` запускает их сам: он передаёт административный DSN тестового кластера в `METAPUS_TEST_INTEGRATIONS_DSN`. Для отдельного запуска задайте `METAPUS_TEST_INTEGRATIONS_DSN` временного PostgreSQL с правом CREATE DATABASE и выполните:

```sh
go test -tags integration -race ./internal/infrastructure/storage/postgres/integration_repo ./internal/infrastructure/storage/postgres/crypto_integration_repo
```

Тесты создают собственные tenant-БД и проверяют шифрование, A → B, старые события, месячный reset, единственный recovery probe, tenant-изоляцию, FK/профили, обновление заполненной тестовой схемы, откат dry-run и повторный импорт. Боевой стенд эти тесты не изменяют.

Подключены RPC (Alchemy, TronGrid, Chainstack Nile и Ethereum Sepolia, GetBlock TRON Nile) и CoinGecko. Использование тех же аккаунтов автоматизациями и поставщиками ресурсов остаётся отдельным этапом F из первоначального плана. Существующие Vault/signing/private seeds не переносятся.

### Ограничение архивного доступа Ethereum Chainstack

Тариф может разрешать свежие блоки и отказывать для архивных высот с JSON-RPC `-32002`. До активации проверьте заголовки, блоки, receipts и logs на глубине, которую требует backfill. День и часовой пояс сброса квоты берите из Billing конкретного аккаунта.

## GetBlock TRON Nile

Создайте один аккаунт с provider `getblock` и двумя именованными ключами:
`fullnode` — токен FullNode REST, `solidity` — токен REST Solidity. Вводится
только токен из ссылки; полный credential URL не сохраняется в RPC. Оба ключа
шифруются и используют одну квоту/ограничение аккаунта, одну trust group `getblock`.
Два API interface не считаются двумя независимыми подтверждениями.

Пул этого аккаунта назначается двум RPC-привязкам сети Nile. Адрес обеих —
`https://shared.eu-central-1.getblock.io`, роли и credential slots соответственно
`fullnode`/`fullnode` и `solidity`/`solidity`, providerId `getblock-nile`, trustGroup
`getblock`. Для резерва выберите приоритет ниже основных источников. У всех
привязок аккаунта должен быть одинаковый минимальный интервал. Transport добавляет
токен перед `/wallet/` либо `/walletsolidity/`, убирает чужие auth headers и
применяет общий процессный account pacer (по умолчанию не более 5 RPS).

Для операторского импорта `integration-config` принимает такой базовый URL и
`apiKeySecretFile` с токеном, а non-secret mapping задаёт slot по роли. Dry-run
откатывает весь импорт; повторное применение не перезаписывает ключи и настройки
сети. На существующей схеме сначала выполните dry-run/apply обновления известных
provider CHECKs. Форма аккаунта и пулов содержит GetBlock.

Перед активацией проверьте свежие и исторические блоки, полный набор receipts и
положительный internal TRX transfer обеих ролей в сравнении с независимым RPC.
HTTP 200 не заменяет такую проверку. Общий 429 временно ограничивает аккаунт;
401/403 переводит версию credentials в invalid. Только явный ответ об исчерпании
месячной квоты фиксируется до следующего настроенного billing period. Точное CU
потребление и тип тарифа не выводятся из количества токенов. Billing reset нужно
сверить с кабинетом владельца.


## Getblock.net — AML/KYT

Профиль `getblock_net` предназначен для AML/KYT и не связан с RPC-профилем `getblock` (Getblock.io). Он принимает один bearer token в slot `default`; RPC URL и ключи `fullnode/solidity` к нему не подходят. Секрет шифруется тем же механизмом integration accounts.

Пакет проверок не имеет календарного сброса. В карточке аккаунта скрыты настройки месячного периода; `nextResetAt` в статусе такого аккаунта равен `null`. Generic RPC transport и проверка RPC-пула не выполняют AML submit. Runtime, конечный локальный бюджет и ограничения включения описаны в [AML runtime](crypto-aml-runtime.md).
