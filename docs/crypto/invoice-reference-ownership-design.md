# Реквизиты мерчанта и системные признаки пополнения

> **TL;DR:** `externalId` и `orderId` принадлежат мерчанту; происхождение инвойса, тип операции и связь с блокчейн-платежом хранятся отдельно.
>
> **Тип:** Reference
>
> **Аудитория:** Developer, AI-Agent
>
> **Статус:** Реализовано и применено к текущему public-test стенду 2026-10-04. Схема изменена в исходной миграции 23; другие действующие tenant-БД автоматически не обновляются.
>
> **Связанные:** [crypto-processing-architecture.md](crypto-processing-architecture.md), [merchant-public-api.md](../reference/merchant-public-api.md)

## 1. Исходное расхождение

В модели `CryptoInvoice.ExternalID` определён как «merchant-owned business reference, not a transport key». Комментарий к колонке `external_id` в миграции также закрепляет её за мерчантом. До исправления автоматическое пополнение persistent-кошелька использовало этот реквизит для внутренних нужд:

- `createTopUpInvoice` записывал `external_id = 'topup_' + txHash`.
- Источник создания наследовался от `NewCryptoInvoice`: `creation_source = 'portal'`, хотя инвойс создавал системный процесс.
- `IsPersistentTopUp` проверял persistent-кошелёк и связанный платёж, включая равенство `i.external_id = 'topup_' || p.tx_hash`.
- `PATCH /merchant/v1/invoices/{id}/reference` принимал обязательный `orderId` и необязательные `metadata`; передать `externalId` через эту команду было нельзя.

При такой SQL-проверке подмена `externalId` реквизитом мерчанта лишала инвойс признака top-up. Исправление переносит классификацию на системные поля и сохраняет связь с исходным платежом.

## 2. Семантика реквизитов

| Реквизит | Владелец и назначение |
|---|---|
| `orderId` / `order_id` | Мерчант: номер заказа, если у операции есть заказ. Пополнение баланса не требует наличия заказа. |
| `externalId` / `external_id` | Мерчант: произвольный бизнес-идентификатор операции, транзакции или учётного документа в 1С/ERP для сверки. |
| `creationSource` / `creation_source` | Платформа: источник создания (`merchant_api`, `portal`, `system`). Автоматический top-up создаётся с источником `system`. |
| `invoice_kind` | Платформа: `payment` для обычного инвойса, `top_up` для автоматического пополнения. Поле не принимается через Merchant API и не сериализуется в публичный JSON модели. |
| Связь с `CryptoPayment` | Платформа: идентифицирует блокчейн-платёж через `invoice_id` и системные поля `network_id`, `tx_hash`, `event_kind`, `event_index`. |
| `Idempotency-Key` | Интегратор передаёт ключ повтора команды; платформа хранит транспортную идемпотентность отдельно от бизнес-реквизитов. |

`creation_source` описывает происхождение записи. Значение `system` само по себе не доказывает, что операция является пополнением: системный процесс может создавать другие инвойсы. Тип top-up определяется явным системным признаком и проверенной связью с persistent-кошельком и платежом.

Инварианты:

- Платформа не записывает технические маркеры или хэши в `externalId` и `orderId` и не резервирует префикс `topup_` в пространстве бизнес-реквизитов мерчанта.
- Мерчант может передать оба бизнес-реквизита независимо. Для пополнения без заказа достаточно `externalId`; до привязки реквизитов оба поля могут быть пустыми.
- Привязка бизнес-реквизитов не меняет распознавание top-up, связь с платежом, суммы, FSM и проводки. При `completed`, `reversed` и reorg тип операции сохраняется.
- Хэш берётся из связанного платежа. Для различения chain events используется вся системная идентичность события, а не один `txHash`.
- Непустые `orderId` и `externalId` независимо уникальны в рамках мерчанта. Присвоенный реквизит нельзя заменить или очистить; пропущенное поле сохраняет значение. Оба переданных реквизита проверяются до записи, конфликт возвращает `409`.

## 3. Реализация и применение схемы

- `NewCryptoInvoice` задаёт `invoice_kind='payment'`. `createTopUpInvoice` устанавливает `top_up` и `creation_source='system'`, оставляя оба бизнес-реквизита пустыми.
- Исходная миграция `00006_crypto_core.sql` определяет тип операции и CHECK: `top_up` возможен только с источником `system`. Доменная валидация проверяет тот же инвариант.
- `IsPersistentTopUp` проверяет тип, источник, принадлежность persistent-кошелька и связанный платёж с совпадающими мерчантом, кошельком, токеном и сетью. Бизнес-реквизиты, статус и каноничность платежа не участвуют в классификации.
- Команда `/reference` принимает `externalId`, `orderId` или оба реквизита; хотя бы один обязателен. Переданные значения содержат 1–255 символов без пробелов по краям и NUL; пустые строки, `null` и нестроковые значения отклоняются. Авторизация выполняется и перед replay.
- Запись реквизитов, увеличение версии и аудит `bind_merchant_reference` с прежними и новыми значениями выполняются в одной транзакции. Повтор с совпадающими данными не создаёт дополнительной записи. DTO, Go/TypeScript/Python SDK и публичная документация поддерживают запрос только с `externalId`, только с `orderId` либо с обоими реквизитами.
- Существующие webhook-снимки сохраняются, включая повторную доставку. Последующие события жизненного цикла содержат актуальные реквизиты; отдельный `invoice.updated` не создаётся. Суммы, проводки и FSM команда привязки не изменяет.

По [правилам миграций](../../db/migrations/README.md) до production изменяется исходная схема и проверяется на отдельных свежих БД. Повторный запуск goose на ранее мигрированной tenant-БД не добавит новую колонку из уже применённой миграции 23. Server и worker новой версии требуют новую схему.

Перенос заполненного стенда выполняется отдельной SQL-транзакцией: до очистки старых `external_id` сохраняются их значения и подтверждённые связи с платежами в миграционном аудите. Старые top-up определяются по проверенным связям и прежнему маркеру, а не только по префиксу. После переноса распознавание использует системный тип; runtime fallback на `topup_<txHash>` отсутствует. Исторические webhook payload не переписываются. Действующие БД этим исправлением не пересоздаются и не очищаются.

На текущем public-test стенде перенесены восемь подтверждённых старых пополнений: `invoice_kind='top_up'`, `creation_source='system'`, `external_id=''`. `order_id` и остальные бизнес-данные сохранены; версия каждого перенесённого инвойса увеличена на один. До возобновления writers проверены обе схемы, все 149 таблиц tenant-БД и восстановление резервных копий обеих БД.
